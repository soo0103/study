# 쿠버네티스 시작하기

## 포드(Pod): 컨테이너를 다루는 기본 단위

### 포드 사용하기

- 포드: 컨테이너 애플리케이션의 기본 단위, 1개 이상의 컨테이너로 구성된 컨테이너의 집합
- 포드는 쿠버네티스에서 컨테이너 애플리케이션을 배포하기 위한 기본 단위
    - 1개의 포드: 1개 혹은 그 이상의 컨테이너가 존재

```yaml
# nginx-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-nginx-pod
spec:
  containers:
    - name: my-nginx-container
      image: nginx:latest
      ports:
        - containerPort: 80
          protocol: TCP
```

- 일반적으로 쿠버네티스 YAML 파일은 apiVersion, kind, metadata, spec 4가지로 구성
    - apiVersion
        - YAML 파일에서 정의한 오브젝트의 API 버전
    - kind
        - 리소스의 종류
        - 생성하려는 것이 포드 → Pod
        - kubectl api-resources 명령어의 KIND 항목에서 리소스 오브젝트 종류 확인 가능
    - metadata
        - 라벨, 주석, 이름 등과 같은 리소스의 부가 정보
    - spec
        - 리소스를 생성하기 위한 정보를 입력
- `kubectl apply -f` 명령어로 생성 가능
- `kubectl get pods <오브젝트 이름>`을 사용하면 특정 오브젝트의 목록 확인 가능
    - 오브젝트 이름 생략 시 존재하는 포드의 목록 출력
- `kubectl describe` 명령어 사용 시 생성된 리소스의 자세한 정보를 얻어올 수 있음
    - 클러스터의 노드로 접속하는 것이 어려운 상황일 경우
        
        ```bash
        kubectl run -i --tty --rm debug \
        	--image=이미지명 --restart=Never bash
        ```
        
- `kubectl exec` 명령으로 포드의 컨테이너에 명령어 전달 가능
    
    ```bash
    kubectl exec -it 포드명 -c 컨테이너명 -- 명령어
    ```
    
- `kubectl logs` 명령어로 포드의 로그 확인 가능
- 오브젝트는 `kubectl delete -f` 명령어로 쉽게 삭제 가능

### 포드 vs 도커 컨테이너

- 쿠버네티스가 포드를 사용하는 이유
    - 여러 리눅스 네임스페이스를 공유하는 여러 컨테이너들을 추상화 된 집합으로 사용하기 위함
- YAML에서 대시(-)를 사용하는 항목은 여러 개의 항목을 정의할 수 있음

<aside>
💡

Pod의 YAML 파일에서 사용되는 command와 args는 컨테이너 내부에서 가장 먼저 실행될 프로세스를 지정

YAML 파일에서 command 설정 시 도커 컨테이너의 Entrypoint로, Pod에서 args를 설정하면 도커 컨테이너의 Cmd(커맨드)로 치환

</aside>

- `kubectl apply -f` 명령을 사용해 YAML 파일 적용
    
    ```bash
    kubectl apply -f nginx-pod-with-ubuntu.yaml
    ```
    
- `kubectl exec` 명령어를 사용해 컨테이너의 내부로 접속 가능
    
    ```bash
    kubectl exec -it my-nginx-pod -c ubuntu-sidecar-container -- bash
    ```
    
- 포드 내의 컨테이너들은 네트워크 네임스페이스 등과 같은 리눅스 네임스페이스를 공유해 사용

<aside>
💡

네트워크 네임스페이스: 컨테이너의 고유한 네트워크 환경을 제공해주는 역할

</aside>

### 완전한 애플리케이션으로서의 포드

- 하나의 포드는 하나의 완전한 애플리케이션
    - Nginx 컨테이너는 그 자체만으로도 완전한 애플리케이션
        
        → 2개의 컨테이너가 정의되는 것은 바람직하지 않음
        
    - 다만, 부가적인 기능을 필요로 한다면 포드의 주 컨테이너를 Nginx로, 기능 확장을 위한 추가 컨테이너를 함께 포드에 포함 가능
        
        → 사이드카 컨테이너: 포드에 정의된 부가적인 컨테이너
        
    - 사이드카 컨테이너는 포드 내의 다른 컨테이너와 네트워크 환경 등을 공유
    - 포드에 포함된 컨테이너들은 모두 같은 워커 노드에서 함께 실행
    
    ⇒ 도커 컨테이너와 쿠버네티스 포드의 차이
    

## 레플리카셋(Replica Set): 일정 개수의 포드를 유지하는 컨트롤러

### 레플리카셋을 사용하는 이유

- YAML에 포드만 정의해 생성하게 되면 이 포드의 생애주기는?
- 포드는 다음의 두 방법으로 삭제 가능
    
    ```bash
    kubectl delete -f nginx-pod-with-ubuntu.yaml
    kubectl delete pods my-nginx-pod
    ```
    
- `kubecl delete` 명령어로 삭제 시 그 포드의 컨테이너 또한 삭제된 뒤 쿠버네티스에서 완전히 삭제
    
    → YAML 파일에 포드만 정의해 생성할 경우 해당 포드는 오직 쿠버네티스 사용자에 의해 관리
    
- 하지만 실제 외부 사용자의 요청을 처리해야 하는 마이크로서비스 구조의 포드라면 이 방식을 사용하기 어려움
    
    → 마이크로 서비스에서는 여러 개의 동일한 컨테이너를 생성한 뒤 외부 요청이 각 컨테이너에 적절히 분배될 수 있어야 함
    
- 가장 쉽게 동일한 포드를 여러 개 생성하는 방법은 다른 이름을 가지는 여러 개의 포드를 직접 만드는 것

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-nginx-pod-a
spec:
  containers:
    - name: my-nginx-container
      image: nginx:latest
      ports:
        - containerPort: 80
          protocol: TCP
---
apiVersion: v1
kind: Pod
metadata:
  name: my-nginx-pod-b
spec:
  containers:
    - name: my-nginx-container
      image: nginx:latest
      ports:
        - containerPort: 80
          protocol: TCP
```

<aside>
💡

YAML 파일은 —-로 구분자로 사용해 여러 개의 리소스를 정의할 수 있음

</aside>

- 직접 생성하는 방법 → 비효율적
- 포드가 어떤 이유로든지 삭제되거나, 포드가 위치한 노드에 장애가 발생해 더 이상 포드에 접근하지 못하게 될 경우, 삭제 후 재생성하지 않는 한 복구되지 않음
- YAML 파일에 정의해 사용하는 방식은 여러 한계가 존재
    
    → 레플리카셋(replicaset)이라는 쿠버네티스 오브젝트를 함께 사용하는 것이 일반적
    
    - 정해진 수의 동일한 포드가 항상 실행되도록 관리
    - 노드 장애 등의 이유로 포드를 사용할 수 없다면 다른 노드에서 포드를 다시 생성

### 레플리카셋 사용하기

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: replicaset-nginx
spec:
	# 레플리카셋 정의
  replicas: 3
  selector:
    matchLabels:
      app: my-nginx-pods-label
  template:
	  # 포드 정의
    metadata:
      name: my-nginx-pod
      labels:
        app: my-nginx-pods-label
    spec:
      containers:
        - name: nginx
          image: nginx:latest
          ports:
            - containerPort: 80
```

- 리소스의 고유한 이름은 포드뿐만 아니라 모든 쿠버네티스 오브젝트에서 설정 가능

<aside>
💡

YAML 파일에서 들여쓰기 된 항목의 이름을 표현하기 위해 상위 항목부터 이름을 표시

ex) name 항목을 metadata.name으로 표현

</aside>

- spec.replicas: 동일한 포드를 몇 개 유지시킬 것인지 결정
- spec.template 아래 내용: 포드가 생성될 때 사용할 템플릿을 정의
    - 보통 포드 스펙 또는 템플릿이라 함

<aside>
💡

kubectl 명령어 사용 시 이름을 줄여쓸 수 있는 오브젝트가 있음

- pods → po
- replicasets → rs
- kubectl api-resources 명령어의 SHORTNAMES 항목에서 확인 가능
</aside>

- 레플리카셋에 정의된 포드의 개수를 늘려 4개가 실행되도록 함
    
    → yaml 파일 수정후 `kubectl apply -f`
    
    - 새로운 리소스를 생성한 것이 아닌 기존의 리소스를 수정
        
        → configured
        
- 레플리카셋 삭제
    
    ```bash
    kubectl delete -f
    kubectl delete rs
    ```
    

### 레플리카셋의 동작 원리

- 레플리카셋은 포드와 연결된 것처럼 보이나 연결돼 있지 않음
    
    → 느슨한 연결 (loosely coupled)을 유지
    
- 느슨한 연결은 포드와 레플리카셋의 정의 중 라벨 셀렉터(Label Selector)를 이용해 이뤄짐
- 포드 생성 시 metadata 항목에서 리소스의 부가적인 정보를 설정할 수 있음
    - 주석, 라벨도 포함
    - 라벨: 포드 등의 쿠버네티스 리소스를 분류할 때 유용하게 사용할 수 있는 메타데이터
- 라벨은 서로 다른 오브젝트가 서로를 찾아야 할 때 사용되기도 함
- 레플리카셋은 `spec.selector.matchLabel`에 정의된 라벨을 통해 생성할 포드를 찾음
    
    → replicas 항목에 정의된 숫자와 일치하지 않으면 템플릿 항목의 내용으로 포드를 생성
    
- 라벨을 가지는 포드를 미리 생성한 다음, 레플리카셋을 생성하면 레플리카셋의 selector.matchLabel에 따라 템플릿에 정의된 포드 설정을 통해 추가적인 개수만 생성
- 삭제 시 포드의 개수가 줄어들었기 때문에 새로운 포드를 생성함

<aside>
💡

레플리카셋과 포드의 라벨은 고유한 키-값 쌍이어야 함

레플리카셋과 동일한 라벨을 가지는 포드를 직접 생성하는 것은 바람직하지 않음

</aside>

- 레플리카셋이 생성해 놓은 포드의 라벨을 삭제한다면 라벨을 삭제한 포드는 레플리카셋에 의해 관리되지 않으며 레플리카셋은 개수를 맞추기 위해 새로운 포드를 생성

```bash
kubectl edit pods replicaset-nginx-2fhd7
```

<aside>
💡

kubectl edit 명령어는 모든 종류의 쿠버네티스 오브젝트에 사용 가능하며 YAML에서 설정하지 않았던 상세한 리소스의 설정까지 확인할 수 있음

</aside>

- 레플리카셋은 일정한 포드의 개수를 유지하는 것
    
    → 설정된 값보다 적으면 포드를 더 생성, 설정된 값보다 많으면 삭제해 포드 개수를 맞춤
    

### 레플리케이션 컨트롤러 vs 레플리카셋

- 레플리케이션 컨트롤러는 표현식 기반의 라벨 셀렉터를 사용
    
    ```yaml
    selector:
    	matchExpressions:
    		- key: app
    			values:
    				- my-nginx-pods-label
    				- your-nginx-pods-label
    			operator: In
    template:
    ...
    ```
    
    - 키가 app인 라벨을 가진 포드 중 values 항목에 정의된 값들이 존재(In)하는 포드들을 대상으로

## 디플로이먼트(Deployment): 레플리카셋, 포드의 배포를 관리

### 디플로이먼트 사용하기

- 대부분 Deployment라는 이름의 오브젝트를  YAML 파일에 정의해 사용
- 디플로이먼트는 레플리카셋의 상위 오브젝트
    
    → 디플로이먼트를 사용하면 포드와 레플리카셋을 직접 생성할 필요 없음
    

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-nginx-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-nginx
  template:
    metadata:
      name: my-nginx-pod
      labels:
        app: my-nginx
    spec:
      containers:
        - name: nginx
          image: nginx:latest
          ports:
            - containerPort: 80
```

- kind 항목 → Deployment로 바뀜

<aside>
💡

디플로이먼트로부터 생성된 레플리카셋과 포드는 특이한 해시값을 포함한 이름으로 생성

해시값은 포드를 정의하는 템플릿으로부터 생성된 것

</aside>

### 디플로이먼트를 사용하는 이유

- 애플리케이션의 업데이트와 배포를 더욱 편하게 만들기 위함
- 디플로이먼트는 컨테이너 애플리케이션을 배포하고 관리하는 역할을 담당
    - 애플리케이션 업데이트 시 레플리카셋의 변경 사항을 저장하는 리비전(revision)을 남겨 롤백을 가능하게 함
    - 무중단 서비스를 위해 포드의 롤링 업데이트 전략을 지정할 수 있음

```yaml
kubectl apply -f deployment-nginx.yaml --record
```

- 포드의 이미지를 변경해야 한다고 가정하면 `kubectl set image` 명령어를 사용할 수 있음
    
    ```yaml
    kubectl set image deployment my-nginx-deployment nginx=nginx:1.11 --record
    ```
    

<aside>
💡

kubectl set image 명령어 대신 YAML 파일에서 직접 image 항목을 변경한 다음 kubectl apply -f 명령어로 적용해도 동일하게 변경

kubectl edit 명령어를 사용해도 됨

</aside>

- 포드 목록 확인 시 새롭게 생성된 포드들이 존재
- 레플리카셋을 확인하면 두 개의 레플리카셋이 나타남
    
    → 디플로이먼트는 포드의 정보가 변경되어 업데이트가 발생했을 때 이전 버전의 레플리카셋을 삭제하지 않고 이전의 정보를 리비전으로서 보전
    
- 리비전 정보 확인
    
    ```bash
    kubectl rollout history deployment my-nginx-deployment
    ```
    
- `--record=true` 옵션으로 디플로이먼트를 변경하면 변경사항을 기록
- `--to-revision`으로 이전 버전의 레플리카셋승로 롤백 가능
    
    ```bash
    kubectl rollout undo deployment my-nginx-deployment --to-revision=1
    ```
    

<aside>
💡

포드 템플릿으로부터 계싼된 해시값은 각 레플리카셋의 라벨 셀렉터에서 pod-template-hash라는 이름의 라벨값으로서 자동으로 설정

→ 여러 개의 레플리카셋은 겹치지 않는 라벨을 통해 포드를 생성

</aside>

- `kubectl describe` 명령어를 사용해 디플로이먼트 정보 출력 시 현재 레플리카셋 리비전 정보와 활성화된 레플리카셋 이름을 확인할 수 있음

## 서비스(Service): 포드를 연결하고 외부에 노출

- 포드 IP는 영속적이지 않아 항상 변할 수 있음
- 여러 개의 디플로이먼트를 하나의 완벽한 애플리케이션으로 연동하려면 포드 IP가 아닌 서로를 발견할 수 있는 다른 방법이 필요
- 쿠버네티스는 디플로이먼트를 생성할 때 포드를 외부로 노출하지 않음
- 디플로이먼트의 YAML 파일에는 포드의 애플리케이션이 사용할 내부 포트만 정의
    
    → `containerPort`
    
- 다른 디플로이먼트의 포드들이 내부적으로 접근하려면 서비스라고 부르는 별도의 쿠버네티스 오브젝트를 생성해야 함
- 서비스의 핵심 기능
    - 여러 개의 포드에 쉽게 접근할 수 있도록 고유한 도메인 이름을 부여
    - 여러 개의 포드에 접근할 때, 요청을 분산하는 로드 밸런서 기능을 수행
    - 클라우드 플랫포믜 로드 밸런서, 클러스터 노드의 포트 등을 통해 포드를 외부로 노출

<aside>
💡

쿠버네티스 설치 시 기본적으로 calico, flannel 등의 네트워크 플러그인을 사용하도록 설정

→ 자동으로 오버레이 네트워크를 통해 각 포드끼리 통신 가능

</aside>

### 서비스(Service)의 종류

- 서비스를 생성하기 전, 디플로이먼트 생성
    
    ```yaml
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: hostname-deployment
    spec:
      replicas: 3
      selector:
        matchLabels:
          app: webserver
      template:
        metadata:
          name: my-webserver
          labels:
            app: webserver
        spec:
          containers:
            - name: my-webserver
              image: alicek106/rr-test:echo-hostname
              ports:
                - containerPort: 80
    ```
    
    ```bash
    # 클러스터의 노드 중 하나에 접속 해 노드에서 curl을 통해 포드로 접근 가능
    kubectl run -i --tty --rm debug \
    --image=alicek106/ubuntu:curl --restart=Never curl localhost | grep Hello
    ```
    
- 서비스는 포드에 어떻게 접근할 것이냐에 따라 종류가 여러 개로 세분화돼 있음
    
    → 목적에 맞는 적절한 서비스 종류를 선택해야 함
    
- 주로 사용하는 서비스 타입
    - ClusterIP 타입
        - 쿠버네티스 내부에서만 포드들에 접근할 때 사용
        - 외부로 포드를 노출하지 않기 때문에 쿠버네티스 클러스터 내부에서만 사용되는 포드에 적합
    - NodePort 타입
        - 포드에 접근할 수 있는 포트를 클러스터의 모든 노드에 동일하게 개방
            
            → 외부에서 포드에 접근할 수 있는 서비스 타입
            
        - 접근할 수 있는 포트는 랜덤으로 정해지나 특정 포트로 접근하도록 설정할 수 있음
    - LoadBalancer 타입
        - 클라우드 플랫폼에서 제공하는 로드 밸런서를 동적으로 프로비저닝해 포드에 연결
        - NodePort 타입과 마찬가지로 외부에서 포드에 접근 가능
        - 일반적으로 클라우드 플랫폼 환경에서만 사용 가능

### ClusterIP 타입의 서비스 - 쿠버네티스 내부에서만 포드에 접근하기

- spec.selector
    - selector 항목은 이 서비스에서 어떠한 라벨을 가지는 포드에 접근할 수 있게 만들 것인지 결정

<aside>
💡

레플리카셋이나 서비스의 selector처럼 두 리소스 간 라벨이 동일할 때만 쿠버네티스의 기능을 온전히 사용할 수 있는 경우가 많음

⇒ 쿠버네티스에서의 라벨은 단순히 리소스의 부가적인 정보를 표시하는 것 이상의 기능을 가질 수 있음

</aside>

- spec.ports.port
    - 생성된 서비스는 쿠버네티스 내부에서만 사용할 수 있는 고유한 IP(ClusterIP)를 할당받음
    - port 항목에는 서비스의 IP에 접근할 때 사요할 포트를 설정
- spec.ports.targetPort
    - selector 항목에서 정의한 라벨에 의해 접근 대상이 된 포트들이 내부적으로 사용하고 있는 포트를 입력
    - containerPort 항목에서 포드가 사용할 포트를 80으로 선언
        
        → targetPort를 80으로 설정
        
        ⇒ 즉 포드 템플릿에 정의된 containerPort와 같은 값으로 설정해야 함
        
- spec.type
    - 이 서비스가 어떤 타입인지 나타냄
    - ClusterIP, NodePort, LoadBalancer 등

<aside>
💡

생성된 서비스 목록 확인 시 kubernetes 이름의 서비스가 미리 생성되어 있음

→ 포드 내부에서 쿠버네티스의 API에 접근하기 위한 서비스

</aside>

- 서비스를 통해 포드에 접근하는 방법은 CLUSTER-IP 항목의 IP와 PORT(S) 항목의 내부 포트를 통해 요청을 보내면 됨
- 서비스를 생성할 때 별도의 설정을 하지 않아도 서비스는 연결된 포드에 대해 로드 밸런싱을 수행
- IP 말고도 서비스 이름 그 자체로도 접근 가능
    - 쿠버네티스는 애플리케이션이 서비스나 포드를 쉽게 찾을 수 있도록 내부 DNS를 구동하고 있으며 포드들은 자동으로 DNS를 사용하도록 설정되기 때문
- 여러 포드가 클러스터 내부에서 서로를 찾아 연결해야 할 때는 서비스의 이르과 같은 도메인 이름을 사용하는 것이 일반적
    
    → 포드간 상호작용은 포드의 IP를 알 필요가 없음, 연결된 서비스 이름을 사용
    

<aside>
💡

서비스의 라벨 셀렉터와 포드의 라벨이 연결되면 쿠버네티스는 자동으로 엔드포인트라고 부른 오브젝트를 별도로 생성

→ 서비스가 가리키고 있는 도착점을 나타냄

엔드포인트도 독립된 쿠버네티스의 리소스

→ 이론상 서비스와 엔드포인트를 따로 만드는 것도 가능

</aside>

### NodePort 타입의 서비스 - 서비스를 이용해 포드를 외부에 노출하기

- NodePort 타입의 서비스는 클러스터 외부에서도 접근 가능
- 모든 노드의 특정 포트를 개방해 서비스에 접근하는 방식
- 도커 스웜 모드에서 컨테이너를 외부로 노출하는 방식과 유사
- type 항목이 NodePort인 것을 제외하고는 동일
- NodePort는 ClusterIP와 동작 방법이 다를 뿐, 동일한 서비스 리소스
- NodePort 타입의 서비스 생성 시 PORT(S) 항목에 출력된 다른 숫자는 모든 노드에서 동일하게 접근할 수 있는 포트를 의미
    
    → 클러스터의 모든 노드에 내부 IP 또는 외부 IP를 통해 31514 포트로 접근하면 동일한 서비스에 연결 가능
    
- GKE, EKS에서 사용하는 경우 방화벽 설정을 해야함

<aside>
💡

각 노드에서 개방되는 포트는 기본적으로 30000~32768 포트 중 랜덤으로 선택

YAML 파일에 nodePort 항목을 정의하면 원하는 포트를 선택할 수 있음

API 서버 컴포넌트의 실행 옵션을 변경하면 원하는 포트를 설정할 수 있음

→ `--service-node-port-range=30000-35000`

</aside>

- NodePort 타입의 서비스는 ClusterIP의 기능을 포함
    
    → NodePort 타입의 서비스는 내부 & 외부 네트워크 양쪽에서 접근할 수 있음
    
- 실제 운영환경에서 NodePort로 서비스를 외부에 제공하는 경우는 많지 않음
    
    → 서비스 그 자체를 통해 서비스를 외부로 제공하기보다는 `인그레스(Ingress)`라고 부르는 쿠버네티스의 오브젝트에서 간접적으로 사용
    

<aside>
💡

특정 클라이언트가 같은 포드로부터만 처리되게 하려면 YAML 파일에서 sessionAffinity  항목을 ClusterIP로 설정

</aside>

### 클라우드 플랫폼의 로드 밸런서와 연동하기 - LoadBalancer 타입의 서비스

- LoadBalancer 타입의 서비스는 서비스 생성과 동시에 로드 밸런서를 새롭게 생성해 포드와 연결
- LoadBalancer 타입의 서비스는 클라우드 플랫폼으로부터 도메인 이름과 IP를 할당받으므로 NodePort보다 더욱 쉽게 접근 가능
- LoadBalancer 타입의 서비스는 로드 밸런서를 동적으로 생성하는 기능을 제공하는 환경에서만 사용 가능
    - 일반적으로 AWS, GCP 같은 클라우드 플랫폼
    - 가상 머신, 온프레미스 환경에서는 어려울 수 있음
- LoadBalancer 타입도 서비스의 IP(ClusterIP)가 할당, 서비스의 IP 또는 서비스의 이름으로 접근 가능
- EXTERNAL-IP와 ports.port에 적힌 포트를 통해 포드에 접근할 수 있음
    - 클라우드 플랫폼에서는 자동으로 할당
- LoadBalancer 타입의 서비스를 생성하면 NodePort의 간접적인 기능 또한 자동으로 사용할 수 있음
- YAML 파일에서 설정을 하지 않으면 AWS 기준 클래식 로드 밸런서를 생성
    - YAML 파일에 metadata.annotation 항목을 정의하면 NLB도 사용 가능
        
        ```yaml
        metadata:
        	annotations:
        		service.beta.kubernetes.io/aws-load-balancer-type: "nlb"
        ```
        

<aside>
💡

annotation은 라벨처럼 해당 리소스의 추가적인 정보를 나타내기 위한 키-값 쌍으로 구성

리소스의 종류에 따라 특정 용도로 사용할 수 있게 미리 정의된 주석이 있음

</aside>

- 온프레미스에서는 MetalLB라는 오픈소스 프로젝트를 사용하면 쉽게 LoadBalancer 타입의 서비스를 사용할 수 있음

### 트래픽의 분배를 결정하는 서비스 속성: externalTrafficPolicy

- LoadBalancer 같은 요청 전달 원리는 경우에 따라 효율적이지 않을 수도 있음
    - 불필요한 네트워크 홉(hop)이 한 단계 더 발생할 수 있음
    - 노드 간 리다이렉트가 발생해 트래픽의 출발지 주소가 바뀌는 SNAT 발생 가능
    - 클라이언트의 IP 주소 또한 보존되지 않을 수 있음
- 요청 전달 메커니즘은 서비스의 속성 중 externalTrafficPolicy 항목에 정의
- `kubectl get -o yaml` 명령어로 서비스의 모든 속성 출력 시 externalTrafficPolicy 확인 가능
    
    ```bash
    kubectl get svc hostname-svc-lb -o yaml
    ```
    
    <aside>
    💡
    
    -o 옵션으로 리소스의 정보를 yaml, json 등의 형식으로 출력 가능
    
    -o 옵션으로 출력하면 쿠버네티스에 의해 자동으로 설정된 상세 항목들까지 모두 확인 가능
    
    </aside>
    
- 기본적으로 설정된 Cluster는 클러스터의 모든 노드에 랜덤한 포트를 개방하는 기본적으로 동작하는 방식
- Local로 설정 시 포드가 생성된 노드에서만 포드로 접근할 수 있으며 로컬 노드에 위치한 포드 중 하나로 요청이 전달
    
    ```yaml
    spec:
      externalTrafficPolicy: Local
    ```
    
- Local로 설정하는 것이 무조건 좋은 것이 아님
    - 각 노드에 포드가 고르지 않게 스케줄링됐을 때, 요청이 고르게 분산되지 않을 수도 있기 때문
    
    → 자원 활용률(utilization) 측면에서 바람직하지 않을 수도 있음
    

### 요청을 외부로 리다이렉트하는 서비스: ExternalName

- 쿠버네티스를 외부 시스템과 연동할 때는 ExternlName 타입의 서비스를 사용할 때도 있음
- 서비스가 외부 도메인을 가리키도록 설정할 수 있음

```yaml
spec:
	type: ExternalName
	externalName: my.database.com
```

- ExternalName 타입의 서비스는 쿠버네티스와 별개로 존재하는 레거시 시스템에 연동해야 하는 상황에서 유용하게 사용할 수 있음
