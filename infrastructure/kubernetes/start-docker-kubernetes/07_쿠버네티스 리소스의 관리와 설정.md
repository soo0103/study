# 쿠버네티스 리소스의 관리와 설정

## 네임스페이스(Namespace): 리소스를 논리적으로 구분하는 장벽

### **네임스페이스 기본 개념**

- 쿠버네티스에서는 리소스를 논리적으로 구분하기 위해 네임스페이스(Namespace)라는 오브젝트를 제공
- 포드, 레플리카셋, 디플로이먼트, 서비스 등과 같은 리소스들이 묶여 있는 하나의 가상 공간 또는 그룹
- 여러 개의 네임스페이스를 사용하면 마치 하나의 클러스터에서 여러 개의 가상 클러스터를 동시에 사용하는 것처럼 느껴짐
- 네임스페이스는 namespace 또는 ns라는 이름으로 쿠버네티스에서 사용할 수 있으며 `kubectl get namespaces` 명령어로 확인 가능
- 기본적으로 3개의 네임스페이스가 존재
- 특정 네임스페이스에 생성된 포드를 확인하려면 kubectl 명령어에 —namespace 옵션을 사용
    
    ```bash
    kubectl get pods --namespace default
    kubectl get pods -n default
    ```
    
- 기본적으로 디플로이먼트나 서비스를 생성하고 삭제했던 작업은 모두 default 네임스페이스에서 수행된 것

<aside>
💡

kube-system 네임스페이스는 클러스터 구성에 필수적인 컴포넌트들과 설정값 등이 존재하는 네임스페이스

⇒ 충분한 이해 없이 건드리지 말것!

</aside>

- 네임스페이스는 라벨보다 더 넓은 용도로 사용할 수 잇음
    - ResourceQuota 오브젝트로 특정 네임스페이스에서 생성되는 포드의 자원 사용량 제한
    - 애드미션 컨드롤러 기능을 이용해 특정 네임스페이스에 생성되는 포드에 항상 사이드카 컨테이너를 붙이도록 설정

### **네임스페이스 사용하기**

- 네임스페이스는 YAML 파일에 정의해 생성 가능

```yaml
apiVersion: v1
kind: Namespace
metadata:
	name: production
```

- 특정 네임스페이스에 리소스를 생성은 metadata.namespace 항목을 설정
    
    ```yaml
    metadata:
    	namespace: production
    ```
    
- kubectl get 명령어에 —all-namespaces 옵션을 사용하면 모든 네임스페이스의 리소스를 확인할 수 있음

### **네임스페이스의 서비스에 접근하기**

- 다른 네임스페이스에 존재하는 서비스에는 서비스 이름만으로 접근할 수 없음
- <서비스 이름>.<네임스페이스 이름>.svc 처럼 이름 뒤에 네임스페이스 이름을 붙이면 다른 네임스페이스의 서비스에도 접근할 수 있음
    
    ```bash
    curl hostname-svc-cluster-ip-ns.production.svc:8080 --silent | grep Hello
    ```
    
- 네임스페이스 삭제 시 존재하는 모든 리소스 또한 삭제되므로 네임스페이스를 삭제하기 전에 리소스 목록을 확인할 것

### **네임스페이스에 종속되는 쿠버네티스 오브젝트와 독립적인 오브젝트**

- 모든 리소스가 네임스페이스에 의해 구분되진 않음
- 포드, 서비스, 레플리카셋, 디플로이먼트는 네임스페이스 단위로 구분
    
    → 오브젝트가 네임스페이스에 속한다(namespaced)
    
- 네임스페이스에 속하는 오브젝트의 종류는 명령어로 확인 가능
    
    ```bash
    kubectl api-resources --namepsaced=true
    ```
    
- 네임스페이스에 속하지 않은 오브젝트들도 존재
    - 노드는 오브젝트 중 하나지만 네임스페이스에 속하지 않는 대표적인 오브젝트
    - nodes는 저수준의 오브젝트이며 네임스페이스에 의해 구분되지 않음
    - 보통 네임스페이스에서 관리되지 않아야 하는, 클러스터 전반에 걸쳐 사용되는 경우가 많음
    - 명령어로 확인 가능
        
        ```bash
        kubectl api-resources --namespaced=False
        ```
        

<aside>
💡

기본적으로 사용하도록 설정되어 있는 네임스페이스는 default

kubeconfig 파일 수정 시 변경 가능

kubens 오픈소스 스크립트로 기본 네임스페이스를 편리하게 변경할 수 있음

```bash
kubens kube-system
```

## 컨피그맵(Configmap), 시크릿(Secret): 설정값을 포드에 전달

- 설정값이나 설정 파일을 애플리케이션에 전달하는 가장 확실한 방법은 도커 이미지 내부에 설정값 또는 설정 파일을 정적으로 저장해 놓는 것
    
    → 유연하게 변경할 수 없다는 단점
    
- 포드 템플릿에 직접 정의하는 것도 방식, 그러나 상황에 따라 환경 변수의 값만 다른 동일한 여러 개의 파일이 존재할 수 있음
- 쿠버네티스는 컨피그맵과 시크릿이라는 오브젝트를 제공
    - 컨피그맵에는 설정값
    - 시크릿에는 노출되어서는 아뇌는 비밀값
- 컨피그맵을 사용하면 1개의 포드 YAML 파일을 사용하되 환경에 따라 다른 컨피그맵을 사용하면 됨

→ 환경 변수나 설정값까지 쿠버네티스 오브젝트에서 관리할 수 있으며 YAML파일로 포드와 함께 배포 가능

### 컨피그맵(Configmap)

#### **컨피그맵 사용 방법 익히기**

- 일반적인 설정값을 담아 저장할 수 있는 쿠버네티스 오브젝트
- 네임스페이스에 속함
    
    → 네임스페이스별로 컨피그맵이 존재
    
- `kubectl create configmap` 명령어로 쉽게 생성 가능, —from-literal 옵션 사용
    
    ```bash
    kubectl create configmap <컨피그맵 이름> <각종 설정값들>
    kubectl create configmap log-level-configmap --from-literal LOG_LEVEL=DEBUG
    ```
    
- —from-literal 옵션을 여러 번 사용함으로써 여러 개의 키-값을 컨피그맵에서 사용하도록 설정 가능
    
    ```bash
    kubectl create configmap start-k8s --from-literal k8s=kubernetes \
    --from-literal container=docker
    ```
    
- 컨피그맵에 저장된 설정값은 `kubectl describe configmap` 명령어나 `kubectl get configmap -o yaml` 명령어로 확인 가능
    
    ```bash
    kubectl get cm
    kubectl get configmap
    
    kubectl describe configmap log-level-configmap
    kubectl get configmap log-level-configmap -o yaml
    ```
    
- 생성된 컨피그맵을 포드에서 사용하려면 YAML 파일에서 포드 템플릿 항목에 컨피그맵을 사용하도록 정의
- 컨피그맵을 포드에서 사용하는 방법
    - 컨피그맵의 값을 컨테이너의 환경 변수로 사용
        - 환경 변수로 가져옴
        - echo $LOG_LEVEL 과 같은 방식으로 확인 가능
    - 컨피그맵의 값을 포드 내부 파일로 마운트해 사용
        - 내부의 특정 파일로 마운트
        - 컨피그맵을 특정 파일로 마운트하면 파일에 값이 저장
        - nginx.conf 등의 파일을 통해 설정값을 읽어들인다면 이 방법이 좋음

#### **컨피그맵의 데이터를 컨테이너의 환경 변수로 가져오기**

```yaml
containers:
	envFrom:
		- configMapRef:
				name: log-level-configmap
		- configMapRef:
				name: start-k8s
```

- 두 개의 컨피그맵으로부터 값을 가져와 환경 변수를 생성
- envFrom 항목은 하나의 컨피그맵에 여러 개의 키-값쌍이 존재해도 모두 가져옴
- 환경 변수 목록을 출력
    
    ```bash
    kubectl exec container-env-example env
    ```
    
- valueFrom과 configMapKeyRef를 사용하면 여러 개의 키-값 쌍이 있는 컨피그맵에서 특정 데이터만을 선택해 환경 변수로 가져올 수 있음
    
    ```yaml
    env:
    	- name: ENV_KEYNAME_1
    		valueFrom:
    			configMapKeyRef:
    				name: log-level-configmap
    				key: LOG_LEVEL
    	- name: ENV_KEYNAME_2
    		valueFrom:
    			configMapKeyRef:
    				name: start-k8s
    				key: k8s
    ```
    

#### **컨피그맵의 내용을 파일로 포드 내부에 마운트하기**

- 애플리케이션이 nginx.conf, mysql.conf 등과 같이 파일로부터 읽어온다면 데이터를 포드 내부의 파일로 마운트해 사용할 수 있음

```yaml
      volumeMounts:
        - name: configmap-volume
          mountPath: /etc/config

  volumes:
    - name: configmap-volume
      configMap:
        name: start-k8s
```

- spec.volumes
    - YAML 파일에서 사용할 볼륨의 목록 정의
    - volumes 항목에서 정의한 볼륨은 spec.containers 항목에서 참조해 사용
- spec.containers.volumeMounts:
    - volumes 항목에서 정의된 볼륨을 컨테이너 내부의 어떤 디렉터리에 마운트할 것인지 명시

```bash
kubectl exec configmap-volume-pod -- ls /etc/config
kubectl exec configmap-volume-pod -- cat /etc/config/k8s
```

- 원하는 키-값 데이터만 선택해 포드에 파일로 가져올 수 있음

```yaml
      volumeMounts:
        - name: configmap-volume
          mountPath: /etc/config

  volumes:
    - name: configmap-volume
      configMap:
        name: start-k8s
        items:
			    - key: k8s
				    path: k8s_fullname # 최종 파일 이름은 k8s_fullname
```

- items: 컨피그맵에서 가져올 키-값 목록
- path: 최종적으로 디렉터리에 위치할 파일의 이름을 입력하는 항목

#### **파일로부터 컨피그맵 생성하기**

- 컨피그맵을 볼륨으로 포드에 제공할 때는 대부분 설정 파일 그 자체를 컨피그맵으로 사용하는 경우가 많음
- 쿠버네티스는 컨피그맵을 파일로부터 생성하는 기능 또한 제공
- 파일로부터 컨피그맵을 생성하려면 `kubectl create configmap` 명령어에 `--from-file` 옵션을 사용
- `--from-env-file` 옵션으로 여러 개의 키-값 형태의 내용으로 구성된 설정 파일을 한꺼번에 컨피그맵으로 가져올 수 있음

#### **YAML 파일로 컨피그맵 정의하기**

- `kubectl create` 명령어에서 `--dry-run`과 `-o yaml` 옵션을 사용하면 컨피그맵을 생성하지 않은 채로 YAML 파일의 내용을 출력할 수 있음
    
    → 출력된 내용을 YAML 파일로 사용하면 컨피그맵 또한 YAML 파일로 배포해 사용 가능
    
    ```bash
    kubectl create configmap my-configmap --from-literal mykey=myvalue \
    --dry-run -o yaml > my-configmap.yaml
    ```
    

<aside>
💡

dry run은 특정 작업의 실행 가능 여부를 검토하는 명령어 또는 API

—dry-run 옵션을 추가하면 실행 가능 여부를 확인할 수 있으며 리소스를 생성하지는 않음

</aside>

- 컨피그맵의 키-값 데이터가 너무 많아지면 YAML 파일의 길이가 불필요하게 길어짐
    
    → kustomize 기능을 사용하면 편하게 컨피그맵 생성 가능
    

### 시크릿(Secret)

#### **시크릿 사용 방법 익히기**

- SSH 키, 비밀번호 등과 같은 민감 정보를 저장하기 위한 용도로 사용
- 네임스페이스에 종속
- 시크릿도 컨피그맵과 유사한 방법으로 사용
- 명령어로 시크릿생성
    
    ```bash
    kubectl create secret genric \
    	my-password --from-literal password=1q2w3e4r
    ```
    
    - —from-file, —from-env-file 옵션으로 가져오는 것도 가능함
- 시크릿은 컨피그맵과는 달리 데이터의 사용 목적에 따라 종류가 나뉨
- 시크릿에 값 저장 시 기본적으로 base64로 인코딩
    
    ```bash
    echo MXEydzNlNHI= | base64 -d
    # 1q2w3e4r
    ```
    
- 시크릿에 저장된 모든 키-값 쌍을 포드의 환경 변수로 가져오려면 YAML 파일에서 secretRef 정의
    
    ```yaml
    apiVersion: v1
    kind: Pod
    metadata:
      name: secret-env-example
    spec:
      containers:
        - name: my-container
          image: busybox
          args: ['tail', '-f', '/dev/null']
          envFrom:
            - secretRef:
              name: my-password
    ```
    
- secretKeyRef로 특정 데이터만 선택해 원하는 이름의 환경 변수로 가져오는 것도 가능함
    
    ```yaml
          env:
            - name: YOUR_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: our-password
                  key: pw2
    
    ```
    
- 키-값 데이터를 포드의 볼륨에 마운트할 수 있으며 선택적으로 사용 가함
    
    ```yaml
          volumeMounts:
            - name: secret-volume
              mountPath: /etc/secret
      volumes:
        - name: secret-volume
          secret:
            secretName: our-password
    ```
    
    ```yaml
          volumeMounts:
            - name: secret-volume
              mountPath: /etc/secret
      volumes:
        - name: secret-volume
          secret:
            secretName: our-password
            items:
              - key: pw1
                path: password1
    
    ```
    
- 시크릿 생성 시 YAML 파일에 base64로 인코딩한 값을 입력했더라도 포드의 환경 변수나 볼륨 파일로서 가져오면 디코딩된 원래의 값을 사용

#### **이미지 레지스트리 접근을 위한 docker-registry 타입의 시크릿 사용하기**

- Opaque 타입
    - 자동으로 설정되는 타입
    - 사용자가 정의하는 데이터를 저장할 수 있는 일반적인 목적의 시크릿
    - generic 명시가 Opaque 타입에 해당하는 종류
- 사설 레지스트리 또는 도커 허브, GCR, ECR 등의 클라우드 레지스트리를 사용하고 있으면 로그인 등의 인증 절차가 필요함
    
    ```yaml
    kubectl create secret docker-registry registry-auth-by-cmd --docker-username=malgeum --docker-password=1q2w3e4r
    ```
    
    - 위 명령어로 생성된 시크릿은 kubernetes.io/dockerconfigjson 타입으로 설정
    - 디플로이먼트 또는 포드 등에서 사설 레지스트리로부터 이미지를 받아올 때 사용할 수 있음
        - YAML 파일에 imagePullSecret을 정의
            
            ```yaml
            spec:
            	containers:
            		- name: test-container
            			image: <이미지명>
            	imagePullSecrets:
            		- name: registry-auth-registry
            ```
            

#### **TLS 키를 저장할 수 있는 tls 타입의 시크릿 사용하기**

- TLS 연결에 사용되는 공개키, 비밀키 등을 자체적으로 저장할 수 있도록 tls 타입을 지원
- 키 페어가 미리 준비되어 있다면 `kubectl create secret tls` 명령어로 쉽게 생성 가능

```bash
kubectl create secret tls my-tls-secret \
	--cert cert.crt --key cert.key
```

- tls.crt, tls.key라는 키로 저장

#### **좀 더 쉽게 컨피그맵과 시크릿 리소스 배포하기**

- —dry-run 명령어에서 출력되는 YAML 파일 내용을 저장해 사용 가능
- 데이터가 많아질수록 직접 시크릿의 데이터를 저장하는 것은 바람직하지 않음
    
    → kustomize 사용
    

```yaml
secretGenerator:
  - name: kustomize-secret
    type: kubernetes.io/tls
    files:
      - tls.crt=cert.crt
      - tls.key=cert.key
```

- 시크릿 생성 전 kustomize로부터 생성될 시크릿 정보를 미리 확인하려면 `kubectl kustomize` 명령어 사용
    
     
    
    ```bash
    kubectl kustomize ./
    ```
    
- `kubectl apply -k ./` 명령어 사용
    
    ```bash
    kubectl apply -k ./
    ```
    
- 컨피그맵의 경우 configmapGenerator 사용
    
    ```yaml
    configmapGenerator:
      - name: kustomize-configmap
        files:
          - tls.crt=cert.crt
          - tls.key=cert.key
    ```
    

<aside>
💡

kustomized로부터 컨피그맵이나 시크릿의 이름 뒤에는 데이터로부터 추출된 해시값이 자동으로 추가

kubectl 명령어 사용 시에도 `--append-hash` 옵션을 이용해 추가 가능

</aside>

#### **컨피그맵이나 시크릿을 업데이트해 애플리케이션의 설정값 변경하기**

- kubectl patch 명령어로 업데이트 가능
    
    ```bash
    sed -i -e 's/myvalue/yourvalue/g' my-configmap.yaml
    ```
    
- 파일로 포드 내부에 마운트된 설정 파일은 변경 시 파일의 내용 또한 자동으로 갱신
- 포드 내부에 마운트된 설정 파일이 변경됐다고 해서 포드에서 실행 중인 애플리케이션의 설정이 자동으로 변경되는 것은 아님
    
    → 변경된 파일을 다시 읽어 들이도록 컨테이너의 프로세스의 별도의 시그널(SIGHUP)을 보내는 사이드카 컨테이너를 포드에 포함시킬 수 있음
