# 모듈

- 테라폼 단일 파일 구성의 문제
    - 테라폼 구성에서 원하는 항목을 찾고 수정하는 것이 점점 어려워짐
    - 리소스들 간의 연관 관계가 복잡해질수록 변경 작업의 영향도를 분석하기 위한 노력이 늘어남
    - 개발/스테이징/프로덕션 환경으로 구분된 경우 비슷한 형태의 구성이 반복되어 업무 효율이 줄어듦
    - 새로운 프로젝트를 구성하는 경우 기존 구성에서 취해야 할 리소스 구성과 종속성 파악이 어려움
- 모듈은 루트 모듈과 자식 모듈로 구분
    - 루트 모듈
        - 테라폼을 실행하고 프로비저닝하는 최상위 모듈
    - 자식 모듈
        - 루트 모듈의 구성에서 호출되는 외부 구성 집합
- 모듈은 테라폼 구성의 집합
    
    → 관리하는 대상의 규모가 커지고 복잡해져 생긴 문제를 보완하고 관리 작업을 수월하게 하기 위한 방안으로 활용
    
    - 관리성
        - 모듈은 서로 연관 있는 구성의 묶음
        - 원하는 구성요소를 단위별로 쉽게 찾고 업데이트 가능
        - 모듈은 다른 구성에서 쉽게 하나으 덩어리로 추가하거나 삭제 가능
        - 모듈이 업데이트되면 이 모듈을 사용하는 모든 구성에서 일관된 변경 작업을 진행할 수 있음
    - 캡슐화
        - 테라폼 구성 내에서 각 모듈은 논리적으로 묶여져 독립적으로 프로비저닝 및 관리되며, 그 결과는 은닉성을 갖춰 필요한 항목만을 외부에 노출시킴
    - 재사용성
        - 테라폼 구성을 모듈화하면 이후에 비슷한 프로비저닝에 이미 검증된 구성을 바로 사용할 수 있음
    - 일관성과 표준화
        - 테라폼 구성 시 모듈을 활용하는 워크플로는 구성의 일관성을 제공하고 서로 다른 환경과 프로젝트에도 이미 검증한 모듈을 적용해 복잡한 구성과 보안 사고를 방지할 수 있음

## 모듈 작성 기본 원칙

- 모듈은 대부분의 프로그래밍 언어에서 쓰이는 라이브러리나 패키지와 역할이 유사함
- 모듈은 기본 작성 원칙을 제안
    - 모듈 디렉터리 형식은 terraform-<프로바이더 이름>-<모듈 이름> 형식을 제안
    - 테라폼 구성은 궁극적으로 모듈화가  가능한 구조로 작성할 것을 제안
    - 각각의 모듈을 독립적으로 관리하기를 제안
    - 공개된 테라폼 레지스트리의 모듈을 참고하기를 제안
- 특정 루트 모듈 하위에 자식 모듈을 구성하는 경우 단순히 복잡한 코드를 분리하는 용도로 명시되며 종속성이 발생하므로 루트 모듈 상위에 모듈 디렉터리를 지정

## 모듈화해보기

- 모듈의 기본적 구조는 테라폼 구성으로 입력 변수를 구성하고 결과를 출력하기 위한 구조로 구성
- 테라폼은 작성된 모듈을 다른 루트 모듈에서 가져다 사용하며 이를 통해 재사용성과 표준화 구조를 구성할 수 있음
- 기존에 작성된 모듈은 다른 모듈에서 참조해 사용할 수 있음
    - 모듈에서 필요한 값은 variable로 선언해 설정
    - 모듈에서 생성된 값 중 외부 모듈에서 참조하고 싶은 값은 output으로 설정

### 자식 모듈 작성 실습

- 하나의 프로비저닝에서 사용자와 패스워드를 여러 번 구성해야 하는 경우를 가상의 시나리오로 함
    - random_pet는 이름을 자동으로 생성, random_password는 사용자의 패스워드를 설정
    - random_password는 random 프로바이더 리소스로 난수 형태로 패스워드를 만들 수 있음
- 자식 모듈과 루트 모듈의 디렉터리 구조
    
    ```bash
    module-training
    └───modules
        ├───root-module # 루트 모듈
        │       main.tf
        │
        └───terraform-random-pwgen # 자식 모듈 홈
                main.tf
                output.tf
                variable.tf
    ```
    
    - 자식 모듈의 main.tf
        
        ```hcl
        resource "random_pet" "name" {
          keepers = {
            ami_id = timestamp()
          }
        }
        
        resource "random_password" "password" {
          length = var.isDB ? 16 : 10
          special = var.isDB ? true : false
          override_special = "!#$%*"
        }
        ```
        
    - variable.tf
        
        ```hcl
        variable "isDB" {
          type = bool
          default = false
          description = "패스워드 대상의 DB 여부"
        }
        ```
        
    - output.tf
        
        ```hcl
        output "id" {
          value = random_pet.name.id
        }
        
        output "pw" {
          value = nonsensitive(random_password.password.result)
        }
        ```
        

### 자식 모듈 호출 실습

- 루트 모듈 정의 예시
    
    ```hcl
    module "mypw1" {
      source = "../modules/terraform-random-pwgen"
    }
    
    module "mypw2" {
      source = "../modules/terraform-random-pwgen"
      isDB = true
    }
    
    output "mypw1" {
      value = module.mypw1
    }
    
    output "mypw2" {
      value = module.mypw2
    }
    ```
    
- 모듈로 묶여진 리소스는 module이라는 정의를 통해 단순하게 재활용하고 반복 사용 가능
- 모듈의 결과 참조 형식은 module.<모듈 이름>.<output 이름>으로 정의
- 루트 모듈에서 사용되는 모듈 정보 정의(modules.json)
    
    ```json
    {"Modules":[{"Key":"","Source":"","Dir":"."},{"Key":"mypw1","Source":"../modules/terraform-random-pwgen","Dir":"../modules/terraform-random-pwgen"},{"Key":"mypw2","Source":"../modules/terraform-random-pwgen","Dir":"../modules/terraform-random-pwgen"}]}
    ```
    

## 모듈 사용 방식

### 모듈과 프로바이더

- 모듈에서 사용되는 모든 리소스는 관련 프로바이더의 정의가 필요함
- 프로바이더 정의를 모듈 안에 두어야 할지 밖에 두어야 할지

#### 유형 1. 자식 모듈에서 프로바이더 정의

- 모듈에서 사용하는 프로바이더 버전과 구성 상세를 자식 모듈에서 고정
- 프로바이더 버전과 구성에 민감하거나, 루트 모듈에서 프로바이더 정의 없이 자식 모듈이 독립적인 구조일 때 고려할 방법
- 모듈에 반복문을 사용할 수 없는 단점이 존재

#### 유형 2. 루트 모듈에서 프로바이더 정의

- 자식 모듈은 루트 모듈의 프로바이더 구성에 종속되는 방식
- 프로바이더 버전과 구성은 루트 모듈의 설정이 적용됨
- 프로바이더를 모듈 내 리소스와 데이터 소스에 일괄 적용하고 자식 모듈에 대한 반복문 사용에 자유로움
- 자식 모듈에 특정 프로바이더 구성의 종속성은 반영할 수 없음
    
    → 자식 모듈을 테스트한 프로바이더 조건을 기록, 자식 모듈을 사용하는 루트 모듈에서 정의하는 프로바이더에 맞게 업데이트
    
- 동일한 모듈에 사용되는 프로바이더 조건이 다른 경우 모듈별로 프로바이더를 매핑하는 예시
    
    ```
    module-training
    ├───modules # 자식 모듈 홈
    │   └───terraform-aws-ec2 
    │           main.tf
    │           output.tf
    │           variable.tf
    │
    └───root-module # 루트 모듈
            main.tf
    ```
    
    ```hcl
    # 자식 모듈 main.tf
    terraform {
      required_providers {
        aws = {
            source = "hashicorp/aws"
        }
      }
    }
    
    resource "aws_default_vpc" "default" {}
    
    data "aws_ami" "default" {
      most_recent = true
      owners = ["amazon"]
    
      filter = {
        name = "owner-alias"
        values = ["amazon"]
      }
    
      filter = {
        name = "name"
        values = ["amzn2-ami-hvm*"]
      }
    }
    
    resource "aws_instance" "default" {
      depends_on = [aws_default_vpc.default]
      ami = data.aws_ami.default.id
      instance_type = var.instance_type
    
      tags = {
        Name = var.insatnce_name
      }
    }
    ```
    
    ```hcl
    # variable.tf
    variable "instance_type" {
      description = "vm 인스턴스 타입 정의"
      default = "t2.micro"
    }
    
    variable "insatnce_name" {
      description = "vm 인스턴스 이름 정의"
      default = "my_ec2"
    }
    ```
    
    ```hcl
    # 자식 모듈 output.tf
    output "private_ip" {
      value = aws_instance.default.private_ip
    }
    ```
    
    ```hcl
    # 루트 모듈 main.tf
    provider "aws" {
      region = "us-west-1"
    }
    
    provider "aws" {
      alias = "seoul"
      region = "ap-northeast-2"
    }
    
    module "ec2_california" {
      source = "../modules/terraform-aws-ec2"
    }
    
    module "ec2_seoul" {
      source = "../modules/terraform-aws-ec2"
      providers = {
        aws = aws.seoul
      }
      instance_type = "m5.large"
    }
    
    terraform {
      required_providers {
        aws = {
            source = "hashicorp/aws"
        }
      }
    }
    ```
    
    ```hcl
    # 루트 모듈 output.tf
    output "module_output_california" {
      value = module.ec2_california.private_ip
    }
    
    output "module_output_seoul" {
      value = module.ec2_seoul.private_ip
    }
    ```
    

### 모듈의 반복문

- 모듈 또한 리소스에서 반복문처럼 구성 가능함
- 모듈이라는 리소스 정의 묶음을 원하는 만큼 프로비저닝할 수 있으므로 리소스 종속성 관리와 유지 보수에 장점이 있음
- count가 적용된 main.tf
    
    ```hcl
    provider "aws" {
      region = "ap-northeast-2"
    }
    
    module "ec2-seoul" {
      count = 2
      source = "../modules/terraform-aws-ec2"
    }
    
    output "module_output" {
      value = module.ec2-seoul[*].private_ip
    }
    ```
    
- 일관된 구성과 구조로 프로비저닝이 되는 경우면 count가 간편한 방안
- 필요한 인수 값이 다르면 for_each
- 동일 모듈에 개발 및 상용에 대한 입력 변수를 다르게 처리하는 예시
    
    ```hcl
    locals {
      env = {
        dev = {
          type = "t3.micro"
          name = "dev_ec2"
        }
        prod = {
          type = "m5.large"
          name = "prod_ec2"
        }
      }
    }
    
    module "ec2_seoul" {
      for_each = local.env
      source = "../modules/terraform-aws-ec2"
      instance_type = each.value.type
      instance_name = each.value.name
    }
    
    output "module_output" {
      value = [
        for k in module.ec2_seoul: k.private_ip
      ]
    }
    ```
    

## 모듈 소스 관리

- Module 블록에 정의된 소스 구성으로 모듈의 코드 위치를 정의
- terraform init을 수행할 때 지정된 모듈을 다운로드해 사용
- 모듈 소스의 유형
    - 로컬 디렉터리 경로
    - 테라폼 레지스트리
    - 깃허브
    - 비트버킷
    - 깃
    - HTTP URLs
    - S3
    - GCS
- 루트 경로에 모듈을 배치하는 것 외에 패키지 하위 디렉터리 경로를 참조하는 것도 하나의 방법

### 로컬 디렉터리 경로

- 로컬 경로를 지정할 때는 하위 디렉터리는 ./로, 상위 디렉터리는 ../로 지정
- 대상 모듈은 다운로드 없이 바로 사용
- 재사용성이 고려되는 경우 상위 디렉터리에 별도 관리하는 것이 좋음
- 항상 루트 모듈과 함께 동작해야 하는 경우 하위 디렉터리에 모듈을 정의

### 테라폼 레지스트리

- 테라폼의 프로토콜을 사용해 모듈을 사용하는 방식
- 공개된 테라폼 모듈을 사용하거나 Terraform Cloud, Terraform Enterprise에서 제공되는 비공개 테라폼 모듈을 사용할 때 설정하는 소스 지정 방식
- 공개된 테라폼 모듈을 source에 선언할 때는 <네임스페이스>/<이름>/<프로바이더> 형태로 설정
- 공개된 레지스트리의 모듈 선언 예시
    
    ```hcl
    module "vpc" {
      source = "terraform-aws-modules/vpc/aws"
      version = "3.14.2"
    }
    ```
    
- 비공개 모듈을 사용할 때는 source 선언 시 주소가 앞에 추가되는 <호스트 이름>/<네임스페이스>/<이름>/<프로바이더>
- 개별 구축된 사설 레지스트리의 모듈 선언 예시
    
    ```hcl
    module "ec2_instance" {
      source = "app.terraform.io/alibaba/ecs-instance/alicloud"
      version = ">= 2.9.0"
    }
    ```
    

### 깃허브

- 깃허브는 테라폼 구성에 대한 CI를 위한 용도로 사용할 수 있음
- 저장된 구성을 테라폼 모듈의 소스로 선언할 수 있음
- source에 github.com으로 시작하는 모듈 위치를 넣어줌
- terraform init 시 깃허브의 모듈을 다운로드하며 .terraform/modules에서 확인 가능함
