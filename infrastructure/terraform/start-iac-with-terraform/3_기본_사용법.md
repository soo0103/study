# 기본 사용법

## 주요 커맨드

- 기본적인 사용법은 terraform 커맨드만 입력하면 출력
    
    ```bash
    terraform
    # Usage: terraform [-version] [-help] <command> [args]
    ```
    

### init

> 기본 사용법: terraform [global options] init [options]
> 
- Prepare your working directory for other commands
- terraform init은 테라폼 구성 파일이 있는 작업 디렉터리를 초기화하는 데 사용
    - 이 작업을 실행하는 디렉터리를 루트 모듈이라 함
    - 테라폼이 실행되는 디렉터리를 모듈이라 부름
    - 모듈에는 테라폼 코드 정의를 위한 tf 또는 tf.json 확장자의 파일, tfvars 같은 변수 정의 파일 포함
    - 호출되는 모듈은 자식 모듈이라 함
- 테라폼을 시작하는 데 사용되는 첫 번째 명령어로 사용되는 프로바이더, 모듈 등의 지정된 버전에 맞춰 루트 모듈을 구성하는 역할을 수행
    - 자바의 pom.xml, Node.js의 package.json, 파이썬의 requirements.txt와 유사
- terraform init 수행 시
    
    ```bash
    $ terraform init
    Initializing the backend...
    Initializing provider plugins...
    - Finding latest version of hashicorp/local...
    - Installing hashicorp/local v2.8.0...
    - Installed hashicorp/local v2.8.0 (signed by HashiCorp)
    Terraform has created a lock file .terraform.lock.hcl to record the provider
    selections it made above. Include this file in your version control repository
    so that Terraform can guarantee to make the same selections by default when
    you run "terraform init" in the future.
    
    Terraform has been successfully initialized!...
    ```
    
    - 테라폼 코드에서 사용된 구문을 기반으로 필요한 프로바이더 플러그인을 찾고 설치하는 과정이 실행됨
    - 프로바이더, 모듈, 백엔드 구성이 설정되고 변경되는 경우에도 실행해야 함

#### -upgrade

- 프로바이더 종속성을 고정시키는 `.terraform.lock.hcl`이 존재
- 작업자가 로컬에서 init으로 받은 프로바이더, 모듈 버전으로 수행한 이후 다른 작업자나 리모트 환경에서 init을 수행하는 경우, 변경된 버전으로 설치될 가능성이 존재
    
    → 당시 버전 정보를 기입, 해당 파일에 명시된 버전으로 init 수행
    
- 의도적으로 버전을 변경하려면 `terraform init -upgrade`를 수행

### validate

> 기본 사용법: terraform [global options] validate [options]
> 
- Check whether the configuration is valid
- 디렉터리에 있는 테라폼 구성 파일의 유효성을 확인
- 대상이 되는 인프라와 서비스의 상태를 확인하기 위한 원격 작업이나 API 작업은 발생하지 않고, 코드적 유효성만 검토
- 작성된 구성의 문법, 종속성, 속성 이름이나 연결된 값의 정확성 확인을 수행

```hcl
# main.tf
resource "local_file" "abc" {
  content  = "abc!"
#  filename = "${path.module}/abc.txt" < 주석 처리
}
```

```bash
$ terraform validate
╷
│ Error: Missing required argument
│
│   on main.tf line 1, in resource "local_file" "abc":
│    1: resource "local_file" "abc" {
│
│ The argument "filename" is required, but no definition was found.
```

#### **-no-color**

- 대부분의 명령어와 사용 가능
- 로컬이 아닌 외부 실행 환경을 사용하는 경우 색상 표기 문자가 표기될 수 있음
    
    → 사용 시 색상 표기 없이  출력
    

#### **-json**

- 실행 결과를 JSON 형식으로 출력
- JSON 형태로 출력 데이터를 이용하면 프로비저닝 과정의 조건 및 데이터로 사용 가능

### plan

> 기본 사용법: terraform [global options] plan [options]
> 
- Show changes required by the current configuration
- terraform plan 명령은 테라폼으로 적용할 인프라의 변경 사항에 관한 실행 계획을 생성하는 동작
- 출력되는 결과를 확인해 어떤 변경이 적용될지 사용자가 미리 검토하고 이해하는 데 도움을 줌
- 변경 사항을 실제로 적용하지는 않음
    - 테라폼 실행 이전의 상태와 비교해 현재 상태가 최신화되었는지 확인
    - 적용하고자 하는 구성을 현재 상태와 비교하고 변경점 확인
    - 구성이 적용되는 경우 대상이 테라폼 구성에 어떻게 반영되는지 확인
- main.tf를 기준으로 plan 시
    
    ```bash
    $ terraform plan
    Acquiring state lock. This may take a few moments...
    
    Terraform used the selected providers to generate the following execution plan. Resource actions are indicated with
    the following symbols:
      + create
    
    Terraform will perform the following actions:
    
      # local_file.abc will be created
      + resource "local_file" "abc" {
          + content              = "abc!"
          + content_base64sha256 = (known after apply)
          + content_base64sha512 = (known after apply)
          + content_md5          = (known after apply)
          + content_sha1         = (known after apply)
          + content_sha256       = (known after apply)
          + content_sha512       = (known after apply)
          + directory_permission = "0777"
          + file_permission      = "0777"
          + filename             = "./abc.txt"
          + id                   = (known after apply)
        }
    
    Plan: 1 to add, 0 to change, 0 to destroy.
    ```
    
    - 생성하는 요소: +로 표시
    - 리소스에 정의 가능한 다른 옵션의 내용과 기본갑시 자동 입력되어 적용
    - 마지막으로 구성을 적용할 경우를 알려줌

#### -detailed-exitcode

- exitcode가 환경 변수로 추가
- 옵션만 추가해서 plan 시
    
    ```bash
    $ terraform plan -detailed-exitcode
    ...
    $ echo $?
    2
    ```
    
    - exitcode 또는 errorlevel은 동작의 결과를 숫자 코드로 제공
        - 0: 변경 사항이 없는 성공
        - 1: 오류가 있음
        - 2: 변경 사항이 있는 성공

#### -out

- -out=<파일명> 형식으로 파일 이름이 정해져 플랜 결과가 생성

### fmt

> 기본 사용법: terraform fmt [options] [DIR]
> 
- Reformat your configuration in the standard style
- format 또는 reformat의 줄임 표시
- 테라폼 구성 파일을 표준 형식과 표준 스타일로 적용하는 데 사용
- 코드 스타일 차이로 생긴 코드 중복 처리가 가능해 업데이트를 최소화하기 가능
- -recursive 옵션 사용 시 하위 디렉터리의 테라폼 구성 파일을 모두 포함해 적용

## HCL

- HCL(HashiCorp configuration language): HashiCorp사에서 IaC와 구성 정보를 명시하기 위해 개발된 오픈 소스 도구
- 코드화된 인프라는 자동화와 더불어 쉽게 버저닝으로 히스토리를 관리하고 함께 작업할 수 있는 기반을 제공

### HCL 사용 이유

- JSON의 경우 구문이 상당히 길어지고 주석이 지원되지 않는 단점이 존재
- YAML의 경우 처음 접하는 사용자가 실제 구조를 만들어내고 익숙해지는 데 어려움이 생기며 관리 대상이 많아지고 복잡해질 경우 리소스 구성을 파악하기 어려움
- HCL vs JSON
    
    ```hcl
    resource "local_file" "abc" {
      content  = "abc!"
      filename = "${path.module}/abc.txt"
    }
    ```
    
    - 변수와 문자열 값을 함께 사용하는 인터폴레이션 표현 방식
    
    ```json
    {
      "resource": [
        {
          "local_file": [
            {"abc": [
                {
                  "content": "abc",
                  "filename": "${path.module}/abc.txt"
                }
              ]
            }
          ]
        }
      ]
    }
    ```
    

### HCL 표현식

```hcl
// 한줄 주석 방법
# 한줄 주석 방법

/*
라인
주석
*/

locals {
	key1 = "value1" # =를 기준으로 키, 값이 구분
    myStr = "UTF-8" # UTF-8 지원
    multiStr = <<EOF # EOF 지원
    Multi
    Line
    String
    with anytext
    EOF # 여러 줄의 스트링은 앞과 끝 문자만 같으면 됨

    boolean1 = true # boolean true
    boolean2 = false # boolean false

    demical = 123 # 기본적으로 10진수
    octal = 0123 # 0으로 시작하는 숫자는 8진수
    hexademical = "0xD5" # 0x 포함하는 스트링은 16진수
    scientific = 1e10 # 과학표기

    # function 호출 예시
    myprojectname = format("%s is my project name", var.project)

    # 삼항 연산자 조건문 지원
    credentials = var.credentials == "" ? file(var.credentials_file): var.credentials
}
```

- 인프라를 구성하기 위한 선언 블록도 다수 존재
    - terraform 블록
    - resource 블록
    - data 블록
    - variable 블록
    - local 블록
    - output 블록

## 테라폼 블록

- 테라폼의 구성을 명시하는 데 사용
- 다른 사람과 함께 작업할 때는 버전을 명시적으로 선언하고 필요한 조건을 입력하여 실행 오류를 최소화할 것을 권장

```hcl
terraform {
  required_version = "~> 1.3.0" # 테라폼 버전

  required_providers { # 프로바이더 버전을 나열
    random = {
      version = ">= 3.0.0, < 3.1.0"
    }
    aws = {
      version = "4.2.0"
    }
  }

  cloud { # Cloud/Enterprise 같은 원격 실행을 위한 정보
    organization = "<My_ORG_NAME>"

    workspaces {
      name = "my-first-workspace"
    }
  }

  backend "local" { # state를 보관하는 위치를 지정
    path = "relative/path/to/terraform.tfstate"
  }
}
```

- 테라폼 내에서 버전이 명시되는 terraform.module에서 사용 가능
- 버전에 대한 제약을 둠으로써 테라폼, 프로바이더, 모듈이 항상 의도한 정의대로 실행되는 것을 목적으로 함
- 버전 체계는 시맨틱 버전 관리 방식을 따름
    - Major 버전
        - 내부 동작의 API가 변경 또는 삭제되거나 하위 호환이 되지 않는 버전
    - Minor 버전
        - 신규 기능이 추가되거나 개선되고 하위 호환이 가능한 버전
    - Patch 버전
        - 버그 및 일부 기능이 개선된 하위 호환이 가능한 버전
- 연산자
    - = 또는 연산자 없음
        - 지정된 버전만을 허용하고 다른 조건과 병기할 수 없음
    - !=: 지정된 버전을 제외
    - >, >=, <, <=: 지정한 버전과 비교해 조건에 맞는 경우 허용
    - ~>: 지정한 버전에서 가장 자리수가 낮은 구성요소만 증가하는 것을 허용
        - ~> x.y인 경우 y버전에 대해서만
        - ~> x.y.z인 경우 z버전에 대해서만 보다 큰 경우를 허용

### 테라폼 버전

- required_version으로 정의
- 지정된 조건과 일치하지 않는 경우 오류를 출력하고 이후 동작을 수행하지 않음
- main.tf에 terraform 블록 추가, 기존 버전보다 낮은 조건으로 선언
    
    ```hcl
    terraform {
      required_version = "< 1.0.0"
    }
    
    resource "local_file" "abc" {
      content  = "abc!"
      filename = "${path.module}/abc.txt"
    }
    ```
    
- terraform init 수행 시
    
    ```bash
    $ terraform init
    Initializing HCP Terraform...
    ╷
    │ Error: Unsupported Terraform Core version
    │
    │   on main.tf line 2, in terraform:
    │    2:   required_version = "< 1.0.0"
    │
    │ This configuration does not support Terraform version 1.14.9. To proceed, either choose another supported
    │ Terraform version or update this version constraint. Version constraints are normally set for good reason, so
    │ updating the constraint may lead to other errors or unexpected behavior.
    ```
    
    - 지원되지 않는 테라폼 버전이라는 메시지가 출력
    - 버전 조건 변경 시 조건 통과함

### 프로바이더 버전

- terraform 블록에서 required_providers에 정의
- v0.13부터 적용
    
    ```hcl
    terraform {
      required_providers {
        aws = {
          source = "hashicorp/aws"
          version = "~> 4.2.0"
        }
        azurerm = {
          source = "hashicorp/azurerm"
          version = ">= 2.99.0"
        }
      }
    }
    ```
    
    - 각 프로바이더의 이름에 소스 경로와 버전을 명시
    - 테라폼 레지스트리 공식 페이지에서 원하는 프로바이더를 선택한 다음 화면에서 우측 상단의 [USE PROVIDER]를 클릭하면 테라폼 코드에 해당 버전을 사용하는 샘플 코드가 표기
- 의도적으로 버전을 높게 설정한 경우
    
    ```hcl
    terraform {
      required_version = ">= 1.0.0"
      required_providers {
        local = {
          source = "hashicorp/local"
          version = ">= 10000.0.0"
        }
      }
    }
    ```
    
    ```bash
    $ terraform init -upgrade
    Initializing the backend...
    Initializing provider plugins...
    - Finding hashicorp/local versions matching ">= 10000.0.0"...
    ╷
    │ Error: Failed to query available provider packages
    │
    │ Could not retrieve the list of available versions for provider hashicorp/local: no available releases match the
    │ given constraints >= 10000.0.0
    │
    │ To see which modules are currently depending on hashicorp/local and what versions are specified, run the following
    │ command:
    │     terraform providers
    ```
    
    - 실제 가용 가능한 버전의 프로바이더가 없으므로 init은 실패

### cloud 블록

- Terraform Cloud, Terraform Enterprise는 CLI, VCS, API 기반의 실행 방식을 지원하고 cloud 블록으로 선언
- cloud 블록 예시
    
    ```bash
    terraform {
      cloud {
        hostname = "app.terraform.io"
        organization = "my-org"
        workspaces {
          name = "my-app-prod" 
        }
      } 
    }
    ```
    

### 백엔드 블록

- 테라폼 실행 시 저장되는 State(상태 파일)의 저장 위치를 선언
- 주의할 점은 **하나의 백엔드만 허용함**
- 테라폼은 State의 데이터를 사용해 코드로 관리된 리소스를 탐색하고 추적
- 협업을 고려하면 테라폼으로 새성한 리소스의 상태 저장 파일을 공유할 수 있는 외부 백엔드 저장소가 필요함
- State에는 외부에 노출되면 안되는 민감 데이터들이 포함될 수 있으므로 State의 접근 제어가 필요함

#### State 잠금 동작

- 기본적으로 활성화되는 백엔드는 local
- 상태를 작업자의 로컬 환경에 저장하고 관리하는 방식
- 다른 백엔드 구성은 동시에 여러 작업자가 접근해 사용할 수 있도록 공유 스토리지 같은 개념을 가짐
- 공유되는 백엔드에 State가 관리되면 테라폼이 실행되는 동안 `.terraform.tfstat.lock.info` 파일이 생성되면서 해당 state를 동시에 사용하지 못하도록 잠금 처리를 함
- 잠금 파일 내부 정보
    
    ```hcl
    {
    	"ID":"a23c85e0-a80f-14f0-ab3f-1be1803091a5",
    	"Operation":"OperationTypeApply",
    	"Info":"",
    	"Who":"LAPTOP-2IRINGL4",
    	"Version":"1.14.9",
    	"Created":"2026-04-23T07:21:46.3075803Z",
    	"Path":"terraform.tfstate"
    }
    ```
    
- -lock=false 옵션으로 잠금을 무시할 수 있음

#### 백엔드 설정 변경

- 백엔드가 설정되면 다시 init 명령을 수행해 State의 위치를 재설정해야 함
- 백엔드 블록에 local을 정의해 terraform init을 수행
    
    ```hcl
    # main.tf
    terraform {
      backend "local" {
        path="state/terraform.tfstate"
      }
    }
    
    resource "local_file" "abc" {
      content  = "abc!"
      filename = "${path.module}/abc.txt"
    }
    ```
    
    ```bash
    $ terraform init
    Initializing the backend...
    Acquiring state lock. This may take a few moments...
    Do you want to copy existing state to the new backend?
      Pre-existing state was found while migrating the previous "local" backend to the
      newly configured "local" backend. No existing state was found in the newly
      configured "local" backend. Do you want to copy this state to the new "local"
      backend? Enter "yes" to copy and "no" to start with an empty state.
    ```
    
    - 백엔드 정보를 테라폼이 내부 메타데이터에 기록한다는 것을 의미
- 새로운 백엔드로의 전환을 위해 두 가지 조건이 제공
    - 이전 구성 유지
        - -migrate-state는 terraform.tfstate의 이전 구성에서 최신의 state 스냅샷을 읽고 기록된 새 구성으로 전환
    - 새로 초기화
        - -reconfigure는 init을 실해하기 전에 terraform.tfstate 파일을 삭제해 테라폼을 처음 사용할 때처럼 이 작업 공간(디렉터리)을 초기화하는 동작
- 기본 동작은 -migrate-state 옵션을 추가해 동작한 것과 동일한 결과를 보여줌
- -reconfigure로 실행하는 경우라면 재구성하므로 백엔드 구성이 변경되었다는 로그를 발견할 수 없음

## 리소스(resource)

- 리소스는 테라폼이 프로비저닝 도구라는 측면에서 가장 중요한 요소
- 리소스 블록은 선언된 항목을 생성하는 동작을 수행

### 리소스 구성

- 리소스 블록은 resource로 시작
- 이후 리소스 블록이 생성할 리소스 유형을 정의
    - 리소스 이름은 첫 번째 언더스코어인 _를 기준으로 앞은 프로바이더 이름, 뒤는 프로바이더 에서 제공하는 리소스 유형을 의미함
        - local_file의 경우 local 프로바이더에 속한 리소스 유형
    - 리소스 유형이 선언되면 뒤에는 고유한 이름을 붙임
        - 이름은 동일한 유형에 대해 식별자 역할을 하기 때문에 유형이 같은 경우에는 같은 이름을 사용할 수 없음
    - 이름 뒤에는 리소스 유혀에 대한 구성 인수들이 중괄호 내에 선언
        - 인수가 필요없는 경우에도 중괄호 입력

```hcl
resource "<리소스 유형>" "<이름>" {
  <인수> = <값>
}

resource "local_file" "abc" {
  content  = "abc!"
  filename = "${path.module}/abc.txt"
}
```

- 리소스에서 사용되는 유형들은 프로바이더에 종속성을 가짐
- 특정 프로바이더의 유형만 추가해도 terraform init 수행 시 해당 프로바이더를 설치
- aws_instance 유형을 추가하고 terraform init 수행
    
    ```hcl
    # main.tf
    resource "local_file" "abc" {
      content = "123!"
      filename = "${path.module}/abc.txt"  
    }
    
    resource "aws_instance" "web" {
      ami = "ami-a1b2c3d4"
      instance_type = "t2.micro"
    }
    ```
    
    ```bash
    $ terraform init
    Initializing the backend...
    Initializing provider plugins...
    - Finding latest version of hashicorp/aws...
    - Finding latest version of hashicorp/local...
    - Installing hashicorp/aws v6.42.0...
    - Installed hashicorp/aws v6.42.0 (signed by HashiCorp)
    - Installing hashicorp/local v2.8.0...
    - Installed hashicorp/local v2.8.0 (signed by HashiCorp)
    ```
    
    - 일반적으로 프로바이더 구성과 함께 사용해야 함
- 리소스는 동작을 보조하기 위한 추가 메타인수를 정의할 수 있음 (timeouts를 제외하고 모든 리소스 정의에 추가 가능함)
    - depends_on
        - 종속성을 선언
        - 선언된 구성요소와의 생성 시점에 대해 정의
    - count
        - 선언된 개수에 따라 여러 리소스를 생성
    - for_each
        - map 또는 set 타입의 데이터 배열의 값을 기준으로 여러 리소스를 생성
    - provider
        - 동일한 프로바이더가 다수 정의되어 있는 경우 지정
    - lifecycle
        - 리소스의 수명주기 관리
    - provisioner
        - 리소스 생성 후 추가 작업 정의
    - timeouts
        - 프로바이더에서 정의한 일부 리소스 유형에서는 create, update, delete에 대한 허용 시간을 정의 가능

### 종속성

- 테라폼의 종속성은 resource, module 선언으로 프로비저닝되는 각 요소의 생성 순서를 구분지음
- 기본적으로 다른 리소스에서 값을 참조해 불러올 경우 생성 선후 관계에 따라 자동으로 연관 관계가 정의되는 암시적 종속성을 가짐
- 강제로 리소스 간 명시적 종속성을 부여할 경우에는 메타인수인 depends_on을 활용
- main.tf에 두 개의 리소스 선언
    
    ```hcl
    resource "local_file" "abc" {
      content = "123!"
      filename = "${path.module}/abc.txt"  
    }
    
    resource "local_file" "def" {
      content = local_file.abc.content # local_file.abc의 속성 값을 대신 넣어줌
      filename = "${path.module}/def.txt"
    }
    ```
    
    ```bash
    $ terraform apply
    ...
    local_file.abc: Creating...
    local_file.abc: Creation complete after 0s [id=5f30576af23a25b7f44fa7f5fdf70325ee389155]
    local_file.def: Creating...
    local_file.def: Creation complete after 0s [id=5f30576af23a25b7f44fa7f5fdf70325ee389155]
    ```
    
    - 리소스 간 종속성이 없는 경우 동일 수준의 구성요소를 실행하는 경우 동시에 생성
    - 특정 리소스의 속성 값이 필요한 경우 해당 리소스가 우선 생성되어야 하므로 프로비저닝 순서가 발생
- terraform graph 명령으로 테라폼이 수행되는 단계를 확인할 수 있음
    
    ```bash
    $ terraform graph
    digraph G {
      rankdir = "RL";
      node [shape = rect, fontname = "sans-serif"];
      "local_file.abc" [label="local_file.abc"];
      "local_file.def" [label="local_file.def"];
      "local_file.def" -> "local_file.abc";
    }
    ```
    
- 리소스의 속성을 주입하지 않아도 두 리소스 간에 종속성이 필요한 경우가 있음
- depends_on을 선언해 종속성을 강제로 적용한 경우
    
    ```hcl
    resource "local_file" "abc" {
      content  = "123!"
      filename = "${path.module}/abc.txt"
    }
    
    resource "local_file" "def" {
      depends_on = [
        local_file.abc # local_file.abc에 대한 종속성을 명시
      ]
    
      content  = "456!"
      filename = "${path.module}/def.txt"
    }
    ```
    
    ```bash
    $ terraform apply
    ...
    local_file.abc: Creating...
    local_file.abc: Creation complete after 0s [id=5f30576af23a25b7f44fa7f5fdf70325ee389155]
    local_file.def: Creating...
    local_file.def: Creation complete after 0s [id=b9fbde4d33ab9c450a7ce303fb4788c9d2db9aed]
    ```
    

### 리소스 속성 참조

- 리소스에서 참조 가능한 값은 인수와 속성
    - 인수
        - 리소스 생성 시 사용자가 선언하는 값
    - 속성
        - 사용자가 설정하는 것은 불가능하지만 리소스 생성 이후 획득 가능한 리소스 고유 값
- 리소스의 인수와 속성 접근
    
    ```bash
    # Terraform Code
    resource "<리소스 유형>" "<이름>" {
      <인수> = <값>  
    }
    
    # 리소스 참조
    <리소스 유형>.<이름>.<인수>
    <리소스 유형>.<이름>.<속성>
    ```
    
- 쿠버네티스 프로바이더의 Namespace 리소스를 생성하고 Secret을 해당 Namespace에 생서하는 종속성을 리소스 인수 값으로 생성하는 예시
    
    ```hcl
    resource "kubernetes_namespace" "example" {
      metadata {
        annotations = {
          name = "example-annotation"
        }
        name = "terraform-example-namespace"
      }
    }
    
    resource "kubernetes_secret" "example" {
      metadata {
        namespace = kubernetes_namespace.example.metadata.0.name # namespace 리소스 인수 참조
        name = "terraform-example"
      }
      data = {
        password = "p4ssw0rd"
      }
    }
    ```
    
    - 리소스 생성 시 사용자가 입력한 인수를 받아 실제 리소스가 생성되면 일부 리소스는 자동으로 기본값이나 추가되는 속성이 부여됨
    - 리소스 문서에 인수는 Arguments로 표현, 리소스 생성 후 추가되는 속성 값으로 Attributes에 안내되어 있음
    - 리소스 속성을 참조하는 다른 리소스 또는 구성요소에서는 생성 후의 속성 값들도 인수로 가져올 수 있음

### 수명주기

- lifecycle은 리소스의 기본 수명주기를 작업자가 의도적으로 변경하는 메타인수
- 메타인수 내 가능한 선언
    - create_before_destroy(bool)
        - 리소스 수정 시 신규 리소스를 우선 생성하고 기존 리소스를 삭제
    - prevent_destroy(bool)
        - 해당 리소스를 삭제하려 할 때 명시적으로 거부
    - ignore_changes(list)
        - 리소스 요소에 선언된 인수의 변경 사항을 테라폼 실해 시 무시
    - precondition
        - 리소스 요소에 선언된 인수의 조건을 검증
    - postcondition
        - plan과 apply 이후의 결과를 속성 값으로 검증

#### create_before_destroy

- 리소스 요소 특성에 따라 선언한 특정 인수 값을 수정하고 프로비저닝을 수행하면 대상을 삭제하고 다시 생성해야 하는 경우가 있음
    - 클라우드 자원의 image가 변경되는 경우 → VM 리소스를 삭제하고 다시 생성
- create_before_destroy가 true로 선언되면 의도한 생성을 실행한 후 삭제로 동작
- 생성되는 리소스가 기존 리소스로 인해 생성이 실패되거나 삭제 시 함께 삭제될 수 있음

```hcl
resource "local_file" "name" {
  content = "lifecycle - step 2"
  filename = "${path.module}/abc.txt"

  lifecycle {
    create_before_destroy = true # 생성 후 삭제
  } 
}
```

#### prevent_destroy

- 작업자가 의도적으로 특정 리소스의 삭제를 방지하고 싶은 경우 사용

```hcl
resource "local_file" "name" {
  content = "lifecycle - step 3"
  filename = "${path.module}/abc.txt"

  lifecycle {
    prevent_destroy = true
  } 
}
```

```bash
$ terraform destroy
│ Error: Instance cannot be destroyed
│
│   on main.tf line 1:
│    1: resource "local_file" "name" {
│
│ Resource local_file.name has lifecycle.prevent_destroy set, but the plan
│ calls for this resource to be destroyed. To avoid this error and continue
│ with the plan, either disable lifecycle.prevent_destroy or reduce the scope
│ of the plan using the -target option.
```

- 테라폼 수명주기에 따라 수해되는 리소스에 prevent_destroy가 활성화되어 있어 삭제가 일어나지 않고 실패함

#### ignore_changes

- 리소스 요소의 인수를 지정해 수정 계획에 변경 사항이 반영되지 않도록 하는 것
- main.tf내용 작성 후 apply
    
    ```hcl
    resource "local_file" "name" {
      content = "lifecycle - step 4"
      filename = "${path.module}/abc.txt"
    
      lifecycle {
        ignore_changes = []
      } 
    }
    ```
    
    ```hcl
    resource "local_file" "name" {
      content = "lifecycle - step 5"
      filename = "${path.module}/abc.txt"
    
      lifecycle {
        ignore_changes = [
          content
        ]
      } 
    }
    ```
    
    ```bash
    $ terraform apply
    local_file.name: Refreshing state... [id=63cd1a0c571d59f5b4337364e612786cc63c1bb8]
    
    No changes. Your infrastructure matches the configuration.
    
    Terraform has compared your real infrastructure against your configuration and
    found no differences, so no changes are needed.
    
    Apply complete! Resources: 0 added, 0 changed, 0 destroyed.
    ```
    
    - 리소스 속성에 변경이 있었으나 ignore_changes의 대상이므로 변경이 발생하지 않음
    - 모든 변경 사항을 무시하려면 ignore_changes = all

#### precondition

- 리소스 생성 이전에 입력된 인수 값을 검증하는 데 사용해 프로비저닝 이전에 미리 약속된 값 이외의 값 또는 필수로 명시해야 하는 인수 값을 검증할 수 있음

```hcl
variable "file_name" {
  default = "step0.txt"
}

resource "local_file" "step6" {
  content = "lifecycle - step 6"
  filename = "${path.module}/${var.file_name}"

  lifecycle {
    precondition {
      condition = var.file_name == "step6.txt"
      error_message = "file name is not \"step6.txt\""
    }
  }
}
```

```bash
$  terraform plan
Acquiring state lock. This may take a few moments...

Planning failed. Terraform encountered an error while generating this plan.

╷
│ Error: Resource precondition failed
│
│   on main.tf line 11, in resource "local_file" "step6":
│   11:       condition = var.file_name == "step6.txt"
│     ├────────────────
│     │ var.file_name is "step0.txt"
│
│ file name is not "step6.txt"
```

- precondition은 프로비저닝해야 하는 클라우드 인프라의 VM을 생성할 때 내부적으로 검증된 이미지 아이디를 사용하는지, 스토리지의 암호화 설정이 되어 있는지 등과 같은 구성을 미리 확인하고 잘못된 프로비저닝을 실행할 수 없도록 구성할 수 있음

#### postcondition

- 프로비저닝 변경 이후 결과를 검증함과 동시에 의존성을 갖는 다른 구성의 변경을 막는 효과가 있음

```hcl
resource "local_file" "step7" {
  content = ""
  filename = "${path.module}/step7.txt"

  lifecycle {
    postcondition {
      condition = self.content != ""
      error_message = "content cannot empty"
    }
  }
}

output "step7_content" {
  value = local_file.step7.id
}
```

```bash
$ terraform apply
...
Plan: 1 to add, 0 to change, 0 to destroy.
╷
│ Error: Resource postcondition failed
│
│   on main.tf line 7, in resource "local_file" "step7":
│    7:       condition = self.content != ""
│     ├────────────────
│     │ self.content is ""
│
│ content cannot empty
```

- 종속성을 갖는 여러 리소스를 구성하는 경우 리소스의 데이터가 다른 리소스 생성 시 활용될 때 원하는 속성이 정의되어야 하는 경우를 확인할 수 있음
- 영향을 받는 다른 리소스가 생성되기 전에 예상되지 않은 프로비저닝 작업을 방지할 수 있음

## 데이터 소스

- 데이터 소스는 테라폼으로 정의되지 않은 외부 리소스 또는 저장된 정보를 테라폼 내에서 참조할 때 사용

### 데이터 소스 구성

- 데이터 소스 블록은 data로 시작
- 이후 데이터 소스 유형을 정의
    - Resource 블록 정의와 유사
- 데이터 소스 인수의 선언과 정의의 예
    
    ```hcl
    data "local_file" "abc" {
      filename = "${path.module}/abc.txt"
    }
    ```
    
    - 데이터 소스 유형은 첫 번째 언더스코어인 _를 기준으로 앞은 프로바이더 이름, 뒤는 프로바이더에서 제공하는 리소스 유형
    - 데이터 소스 유형을 선언한 뒤에는 고유한 이름을 붙임
        - 이름은 동일한 유형에 대해 식별자 역할을 하므로 중복될 수 없음
    - 이름 뒤에는 데이터 소스 유형에 대한 구성 인수들은 {} 안에 선언
        - 인수가 필요하지 않은 유형도 {}를 입력
- 데이터 소스를 정의할 때 사용 가능한 메타인수
    - depends_on
        - 종속성을 선언하며, 선언된 구성요소와의 생성 시점에 대해 정의
    - count
        - 선언된 개수에 따라 여러 데이터 소스를 선언
    - for_each
        - map 또는 set 타입의 데이터 배열의 값을 기준으로 여러 리소스를 생성
    - provider
        - 동일한 프로바이더가 다수 정의되어 있는 경우 지정
    - lifecycle
        - 데이터 소스의 수명주기 관리

### 데이터 소스 속성 참조

- 데이터 소스로 읽은 대상을 참조하는 방식은 리소스와 구별되게 data가 앞에 붙음
- 데이터 소스 인수의 선언과 참조 방식
    
    ```hcl
    # Terraform Code
    data "<리소스 유형>" "<이름>" {
      <인수> = <값>
    }
    
    # 데이터 소스 참조
    data.<리소스 유형>.<이름>.<속성>
    ```
    
- AWS 프로바이더의 가용영역을 작업자가 수동으로 입력하지 않고 프로바이더로 접근한 환경에서 제공되는 데이터 소스를 활용해 subnet의 가용영역 인수를 정의하는 예시
    
    ```hcl
    # Declare the data source
    data "aws_availability_zones" "available" {
      state = "available"
    }
    
    resource "aws_subnet" "primary" {
      availability_zone = data.aws_availability_zones.available.names[0]
      # e.g. ap-northeast-2a
    }
    
    resource "aws_subnet" "secondary" {
      availability_zone = data.aws_availability_zones.available.names[1]
      # e.g. ap-northeast-2b  
    }
    ```
    
- 데이터 소스 활용의 예
    
    ```hcl
    resource "local_file" "abc" {
      content = "123!"
      filename = "${path.module}/abc.txt"
    }
    
    data "local_file" "abc" {
      filename = local_file.abc.filename
    }
    
    resource "local_file" "def" {
      content = data.local_file.abc.content
      filename = "${path.module}/def.txt"
    }
    ```
    
    ```bash
    $ terraform apply
    ...
    local_file.abc: Creating...
    local_file.abc: Creation complete after 0s [id=5f30576af23a25b7f44fa7f5fdf70325ee389155]
    data.local_file.abc: Reading...
    data.local_file.abc: Read complete after 0s [id=5f30576af23a25b7f44fa7f5fdf70325ee389155]
    local_file.def: Creating...
    local_file.def: Creation complete after 0s [id=5f30576af23a25b7f44fa7f5fdf70325ee389155]
    
    Apply complete! Resources: 2 added, 0 changed, 0 destroyed.
    ```
    
    - 데이터 소스 data.local_file.abc는 리소스 local_file.abc의 파일 이름을 참조해 데이터 소스를 생성
    - 데이터 소스 local_file은 읽어온 파일의 내용을 content 속성으로 참조할 수 있음
    - local_file.def에서는 data.local_file.abc.content로 읽혀진 데이터를 참조

## 입력 변수(variable)

- 인프라를 구성하는 데 필요한 속성 값을 정의해 코드의 변경 없이 여러 인프라를 생성하는 데 목적이 있음
    
    → 입력 변수로 정의
    
- 테라폼은 plan 수행 시 값을 입력함

### 변수 선언 방식

- 변수는 variable로 시작되는 블록으로 구성
- 변수 블록 뒤의 이름 값은 동일  모듈 내 모든 변수 선언에서 고유해야 하며 이 이름으로 다른 코드 내에서 참조
    
    ```hcl
    variable "<이름>" {
      <인수> = <값>
    }
    
    variable "image_id" {
      type = string
    }
    ```
    
- 테라폼 코드 구성에 미리 예약되어 있어 변수 이름으로 사용 불가능한 이름
    - source
    - version
    - providers
    - count
    - for_each
    - lifecycle
    - depends_on
    - locals
- 변수 정의 시 사용 가능한 메타인수
    - default
        - 변수에 할당되는 기본값 정의
    - type
        - 변수에 허용되는 값 유형 정의
    - description
        - 입력 변수의 설명
    - validation
        - 변수 선언의 제약조건을 추가해 유효성 검사 규칙을 정의
    - sensitive
        - 민감한 변수 값임을 알리고 테라폼의 출력문에서 값 노출을 제한
    - nullable
        - 변수의 값이 없어도 됨을 지정

### 변수 유형

- 지원되는 변수의 범주와 형태
    - 기본 유형
        - string
        - number
        - bool
        - any: 명시적으로 모든 유형이 허용됨을 표시
    - 집합 유형
        - list(<유형>): 인덱스 기반 집합
        - map(<유형>): 값=속성 기반 집합이며 키값 기준 정렬
        - set(<유형>): 값 기반 집합이며 정렬 키값 기준 정렬
        - object({<인수 이름=<유형>, …})
        - tuple([<유형>, …])
- 변수 유형별 선언 방식의 예
    
    ```hcl
    variable "string" {
      type        = string
      description = "var String"
      default     = "myString"
    }
    
    variable "number" {
      type    = number
      default = 123
    }
    
    variable "boolean" {
      default = true
    }
    
    variable "list" {
      default = [
        "google",
        "vmware",
        "amazon",
        "microsoft"
      ]
    }
    
    output "list_index_0" {
      value = var.list.0
    }
    
    output "list_all" {
      value = [
        for name in var.list :
        upper(name)
      ]
    }
    
    variable "map" {
      default = {
        aws   = "amazon",
        azure = "microsoft",
        gcp   = "google"
      }
    }
    
    variable "set" {
      type = set(string)
      default = [
        "google",
        "vmware",
        "amazon",
        "microsoft"
      ]
    }
    
    variable "object" {
      type = object({
        name = string,
        age  = number
      })
      default = {
        name = "abc"
        age  = 12
      }
    }
    
    variable "tuple" {
      type    = tuple([string, number, bool])
      default = ["abc", 123, true]
    }
    
    variable "ingress_rules" {
      type = list(object({
        port        = number,
        description = optional(string),
        protocol    = optional(string, "tcp")
      }))
      default = [
        { port = 80, description = "web" },
        { port = 53, protocol = "udp" }
      ]
    }
    ```
    

### 유효성 검사

- 입력되는 변수 타입 지정 외에 사용자 지정 유효성 검사가 가능함
- 변수 블록 내 validation 블록에서 조건인 condition에 지정되는 규칙이 true/false를 반환해야 함
- error_message는 condition의 값이 false인 경우 출력되는 메시지를 정의
- regex 함수는 대상의 문자열에 정규식을 적용하고 일치하는 문자열을 반환
    - can 함수를 함께 사용 시 정규식에 일치하지 않는 경우의 오류를 검출
- validation 블록은 중복 선언 가능
- variable 유효성 검사의 예
    
    ```hcl
    variable "image_id" {
      type = string
      description = "The id of the machine image (AMI) to use for the server."
    
      validation {
        condition = length(var.image_id) > 4
        error_message = "The image_id value must exceed 4."
      }
    
      validation {
        # regex(...) fails if it cannot find a match
        condition = can(regex("^ami-", var.image_id))
        error_message = "The image_id value must starting with \"ami-\"."
      }
    }
    ```
    

### 변수 참조

- variable은 코드 내에서 var.<이름>으로 참조
- variable의 값 참조의 예
    
    ```hcl
    variable "my_password" {}
    
    resource "local_file" "abc" {
      content = var.my_password
      filename = "${path.module}/abc.txt"
    }
    ```
    
    - 선언된 variable에 정의된 값이 없으므로 plan 또는 apply 실행 후 변수 값을 입력하라는 항목을 확인할 수 있음
    
    ```bash
    $ terraform plan
    Acquiring state lock. This may take a few moments...
    var.my_password
      Enter a value
    ```
    

### 민감한 변수 취급

- 민감한 입력 변수를 위해 입력 변수의 민감 여부를 선언할 수 있음
- 변수 선언에 sensitive를 추가
    
    ```hcl
    variable "my_password" {
      default = "password"
      sensitive = true
    }
    
    resource "local_file" "abc" {
      content = var.my_password
      filename = "${path.module}/abc.txt"
    }
    ```
    
    - 테라폼의 계획 출력에서 참조되는 변수 값이 (sensitive)로 감춰지는 것을 확인할 수 있음
    
    ```hcl
    $ terraform apply
    
    Terraform used the selected providers to generate the following execution plan.
    Resource actions are indicated with the following symbols:
      + create
    
    Terraform will perform the following actions:
    
      # local_file.abc will be created
      + resource "local_file" "abc" {
          + content              = (sensitive value)
          + content_base64sha256 = (known after apply)
    ...
    ```
    

### 변수 입력 방식과 우선순위

- 선언되는 방식에 따라 변수의 우선순위가 있음
    - 로컬 환경과 빌드 서버 환경에서의 정의를 다르게 하거나
    - 프로비저닝 파이프라인을 구성하는 경우 외부 값을 변수에 지정 가능
- 입력 변수의 우선순위를 파악하기 위한 예시
    
    ```hcl
    variable "my_var" {}
    
    resource "local_file" "abc" {
      content = var.my_var
      filename = "${path.module}/abc.txt"
    }
    ```
    
    - 적용되는 변수는 resoure.local_file.abc의 content 인수의 결과로 확인 가능
    - 우선순위 수준의 숫자가 작을수록 우선순위도 낮음
        - 우선순위 수준 1: 실행 후 입력
        - 우선순위 수준 2: variable 블록의 default 값
        - 우선순위 수준 3: 환경 변수(TF_VAR_변수 이름)
        - 우선순위 수준 4: terraform.tfvars에 정의된 변수 선언
        - 우선순위 수준 5: *.auto.tfvars에 정의된 변수 선언
        - 우선순위 수준 6: *.auto.tfvars.json에 정의된 변수 선언
        - 우선순위 수준 7: CLI 실행 시 -var 인수에 지정 또는 -var-file로 파일 지정

## local(지역 값)

- 코드 내에서 사용자가 지정한 값 또는 속성 값을 가공해 참조 가능한  local은 외부에서 입력되지 않고 코드 내에서만 가공되어 동작하는 값을 선언
- local은 선언된 모듈 내에서만 접근 가능
- 실행 시 입력받을 수 없음
- 빈번하게 여러 곳에서 사용되는 경우 실제 값에 대한 추적이 어려워져 유지 관리 측면에서 부담 발생 가능

### local 선언

- 로컬이 선언되는 블록은 locals로 시작
- 선언되는 인수에 표현되는 값은 상수, 리소스의 속성, 변수의 값들을 조합해 정의 가능
- locals에 선언한 로컬 변수 이름은 전체 루트 모듈 내에서 유일해야 함
- local 값 선언 방식의 예
    
    ```hcl
    variable "prefix" {
      default = "hello"
    }
    
    locals {
      name = "terraform"
      content = "${var.prefix} ${local.name}"
      my_info = {
        age = 20
        region = "KR"
      }
      my_nums = [1, 2, 3, 4, 5]
    }
    
    locals {
      content = "content2" # 중복 선언으로 오류 발생
    }
    ```
    

### local 참조

- 선언된 local 값은 local.<이름>으로 참조
- 구성 파일을 여러 개 생성해 작업하는 경우 서로 다른 파일에 선언되어 있더라도 다른 파일에서 참조 가능
- 테라폼 구성 예시
    
    ```hcl
    # main.tf
    variable "prefix" {
      default = "hello"
    }
    
    locals {
      name = "terraform"
    }
    
    resource "local_file" "abc" {
      content = local.content # sub.tf에서 정의된 로컬 값
      filename = "${path.module}/abc.txt"
    }
    ```
    
    ```hcl
    # sub.tf
    locals {
      content = "${var.prefix} ${local.name}"
    }
    ```
    
    - terraform plan 시 main.tf의 content 내용을 값으로 local.content를 참조
    - 실행 시점에는 마치 하나의 구성 파일처럼 올바로 표기되는 것을 확인할 수 있음

## 출력(output)

- 주로 테라폼 코드의 프로비저닝 수행 후의 결과 속성 값을 확인하는 용도로 사용
- 테라폼 모듈 간, 워크스페이스 간 데이터 접근 요소로 활용할 수 있음
    - java의 getter와 비슷함
- 출력 값의 용도
    - 루트 모듈에서 사용자가 확인하고자 하는 특성 속성 출력
    - 자식 모듈의 특정 값을 정의하고 루트 모듈에서 결과를 참조
    - 서로 다른 루트 모듈의 결과를 원격으로 읽기 위한 접근 요소
- 출력 값 작성 시 속성 값을 노출하고 접근할 수 있음
    
    → 협업 시 유리
    

### output 선언

- 모듈 내에서 생성되는 속성 값들은 output 블록에 정의
- output 블록 작성 예시
    
    ```hcl
    output "instance_ip_addr" {
      value = "http://${aws_instance.server.private_ip}"
    }
    ```
    
    - 출력되는 값은 value 값
    - 리소스 생성 후 결정되는 속성 값은 프로비저닝이 완료되어야 최종적으로 결과 확인 가능
        
        → terraform plan 단계에서는 적용될 값을 출력하지 않음
        
- 변수 정의 시 사용 가능한 메타인수
    - description
        - 출력 값 설명
    - sensitive
        - 민감한 출력 값임을 알리고 테라폼 출력문에서 값 노출을 제한
    - depends_on
        - value에 담길 값이 특정 구성에 종속성이 있는 경우 생성되는 순서를 임의로 조정
    - precondition
        - 출력 전에 지정된 조건을 검증

### output 활용

- output 블록 동작 확인 예시
    
    ```hcl
    resource "local_file" "abc" {
      content = "abc123"
      filename = "${path.module}/abc.txt"
    }
    
    output "file_id" {
      value = local_file.abc.id
    }
    
    output "file_abspath" {
      value = abspath(local_file.abc.filename)
    }
    ```
    
    ```bash
    $ terraform plan
    ...
    Changes to Outputs:
      + file_abspath = "C:/User/Desktop/cs/terraform/abc.txt"
      + file_id      = (known after apply)
    ```
    
    ```bash
    $ terraform apply
    ...
    Outputs:
    
    file_abspath = "C:/Users/Desktop/cs/terraform/abc.txt"
    file_id = "6367c48dd193d56ea7b0baad25b19455e529f5ee"
    ```
    
    ```bash
    $ terraform output
    file_abspath = "C:/Users/Desktop/cs/terraform/abc.txt"
    ```

## 반복문

- list 형태의 값 목록이나 Key-Value 형태의 문자열 집합인 데이터가 있는 경우 동일한 내용에 대해 테라폼 구성 정의를 반복적으로 하지 않고 관리할 수 있음

### count

- 리소스 또는 모듈 블록에 count 값이 정수인 인수가 포함된 경우 선언된 정수 값만큼 리소스나 모듈을 생성하게 됨
- 생성되는 참조값은 count.index
- 반복하는 경우 0부터 인덱스가 부여
- count 예시
    
    ```hcl
    resource "local_file" "abc" {
      count    = 5
      content  = "abc"
      filename = "${path.module}/abc.txt"
    }
    ```

- count.index를 추가

### for_each

- 리소스 또는 모듈 블록에서 for_each에 입력된 데이터 형태가 map이나 set이면 선언된 key 개수만큼 리소스를 생성
- for_each 반복문 예시
    
    ```hcl
    resource "local_file" "abc" {
      for_each = {
        a = "content a"
        b = "content b"
      }
      content = each.value
      filename = "${path.module}/${each.key}.txt"
    }
    ```
    
    - each.key: 이 인스턴스에 해당하는 map 타입의 key값
    - each.value: 이 인스턴스에 해당하는 map타입의 value값
- 생성되는 리소스의 경우 <리소스 타입>.<이름>[<key>]
- 모듈의 경우 module.<모듈이름>[<key>]로 해당 리소스의 값을 참조
- 참조 방식으로 리소스 간 종속성을 정의하거나 변수로 다른 리소스에서 사용하거나 출력 값으로 사용
- 반복 참조하는 for_each 예시
    
    ```hcl
    variable "names" {
      default = {
        a = "content a"
        b = "content b"
        c = "content c"
      }
    }
    
    resource "local_file" "abc" {
      for_each = var.names
      content = each.value
      filename = "${path.module}/abc-${each.key}.txt"
    }
    
    resource "local_file" "def" {
      for_each = local_file.abc
      content = each.value.content
      filename = "${path.module}/def-${each.key}.txt"
    }
    ```
    
    - key 값은 count의 index와 달리 고유함
        
        → 중간에 값을 삭제한 후 다시 적용해도 삭제한 값에 대해서만 리소스를 삭제
        
    
    ```hcl
    variable "names" {
      default = {
        a = "content a"
        c = "content c"
      }
    }
    ```
    

### for

- 복합 형식 값의 형태를 변환하는 데 사용
- list 값의 포맷을 변경하거나 특정 접두사(prefix)를 추가
- output에 원하는 형태로 반복적인 결과를 표현
    - list 타입의 경우 값 또는 인덱스와 값을 반환
    - map 타입의 경우 키 또는 키와 값에 대해 반환
    - set 타입의 경우 키 값에 대해 반환
- list 내용을 파일에 담는 리소스 생성 예시
    
    ```hcl
    variable "names" {
      default = ["a", "b", "c"]
    }
    
    resource "local_file" "abc" {
      content = jsonencode(var.names)
      filename = "${path.module}/abc.txt"
    }
    ```
    
- var.name의 값을 일괄적으로 대문자로 변환하는 예시
    
    ```hcl
    variable "names" {
      default = ["a", "b", "c"]
    }
    
    resource "local_file" "abc" {
      content = jsonencode([for s in var.names: upper(s)])
      filename = "${path.module}/abc.txt"
    }
    ```
    
- for 구문 사용하는 규칙
    - list 유형의 경우 반환 받는 값이 하나로 되어 있으면 값을, 두 개인 경우 앞의 인수가 인덱스를 반환하고 뒤의 인수가 값을 반환(관용적으로 인덱스는 i, 값은 v)
    - map 유형의 경우 반환 받는 값이 하나로 되어 있으면 키, 두 개인 경우 앞의 인수가 키, 뒤의 인수가 값을 반환(관용적으로 키는 k, 값은 v)
    - 결과 값은 for문을 묶는 기호가 []인 경우 tuple로 반환, {}인 경우 object 형태로 반환
    - object 형태의 경우 키와 값에 대한 쌍은 => 기호로 구분
    - {} 형식을 사용해 object 형태로 결과를 반환하는 경우 키 값은 고유해야 하므로 값 뒤에 그룹화 모드 심볼(…)을 붙여서 키의 중복을 방지
    - if 구문을 추가해 조건 부여 가능
- list 유형에 대한 for 구문 처리 예시
    
    ```hcl
    variable "names" {
      type = list(string)
      default = ["a", "b"]
    }
    
    output "A_upper_value" {
      value = [for v in var.names: upper(v)]
    }
    
    output "B_index_and_value" {
      value = [for i, v in var.names: "${i} is ${v}"]
    }
    
    output "C_make_object" {
      value = {for v in var.names: v => upper(v)}
    }
    
    output "D_with_filter" {
      value = [for v in var.names: upper(v) if v != "a"]
    }
    ```
    
    ```bash
    $ terraform apply
    ...
    Outputs:
    
    A_upper_value = [
      "A",
      "B",
    ]
    B_index_and_value = [
      "0 is a",
      "1 is b",
    ]
    C_make_object = {
      "a" = "A"
      "b" = "B"
    }
    D_with_filter = [
      "B",
    ]
    ```
    
- map 유형에 대한 for 구문 예시
    
    ```hcl
    variable "members" {
      type = map(object({
        role = string
      }))
    
      default = {
        ab = {role = "member", group = "dev"}
        cd = {role = "admin", group = "dev"}
        ef = {role = "member", group = "ops"}
      }
    }
    
    output "A_to_tuple" {
      value = [for k, v in var.members: "${k} is ${v.role}"]
    }
    
    output "B_get_only_role" {
      value = {
        for name, user in var.members: name => user
        if user.role == "admin"
      }
    }
    
    output "C_group" {
      value = {
        for name, user in var.members: user.role => name...
      }
    }
    ```
    
    ```bash
    $ terraform apply
    ...
    Outputs:
    
    A_to_tuple = [
      "ab is member",
      "cd is admin",
      "ef is member",
    ]
    B_get_only_role = {
      "cd" = {
        "role" = "admin"
      }
    }
    C_group = {
      "admin" = [
        "cd",
      ]
      "member" = [
        "ab",
        "ef",
      ]
    }
    
    ```
    

### dynamic

- 리소스 내에 선언되는 구성 블록을 다중으로 작성해야 하는 경우가 있음
    - AWS의 Security Goup 리소스 구성에 ingress, egress 요소가 리소스 선언 내부에서 블록 형태로 여러 번 정의되는 경우
        
        ```hcl
        resource "aws_security_group" "allow_tls" {
          name = "allow_tls"
          description = "Allow TLS inbound traffic"
          vpc_id = aws_vpc.main.id
        
          ingress {
            description = "TLS from VPC"
            from_port = 443
            to_port = 443
            protocol = "tcp"
            cidr_blocks = [aws_vpc.main.cidr_block]
            ipv6_cidr_blocks = [aws_vpc.main.ipv6_cidr_block]
          }
        
          ingress {
            description = "HTTP"
            from_port = 8080
            to_port = 8080
            protocol = "-1"
            cidr_blocks = [aws_vpc.main.cidr_block]
            ipv6_cidr_blocks = [aws_vpc.main.ipv6_cidr_block]
          }
        
          egress {
            from_port = 0
            to_port = 0
            protocol = "-1"
            cidr_blocks = ["0.0.0.0/0"]
            ipv6_cidr_blocks = ["::/0"]
          }
        
          tags = {
            Name = "allow_tls"
          }
        }
        ```
        
        - 리소스 내 블록 속성은 리소스 자체의 반복 선언이 아닌 내부 속성 요소 중 블록으로 표현되는 부분에 대해서만 반복 구문을 사용해야 하므로 dynamic 블록을 사용해 동적인 블록 생성 가능
- dynamic 블록 작성은 기존 블록의 속성 이름을 dynamic 블록의 이름으로 선언하고 기존 블록 속성에 정의되는 내용을 content 블록에 작성
- 반복문 구문은 for_each 사용
- dynamic에서는 dynamic에 지정한 이름에 대해 속성이 부여
- 리소스 내 반복적으로 선언되는 구성 블록
    
    ```hcl
    data "archive_file" "dotfiles" {
      type = "zip"
      output_path = "${path.module}/dotfiles.zip"
    
      source {
        content = "hello a"
        filename = "${path.module}/a.txt"
      }
    
      source {
        content = "hello b"
        filename = "${path.module}/b.txt"
      }
    
      source {
        content = "hello c"
        filename = "${path.module}/c.txt"
      }
    }
    ```
    
    ```hcl
    variable "names" {
      default = {
        a = "hello a"
        b = "hello b"
        c = "hello c"
      }
    }
    
    data "archive_file" "dotfiles" {
      type = "zip"
      output_path = "${path.module}/dotfiles.zip"
    
      dynamic "source" {
        for_each = var.names
        content {
          content = source.value
          filename = "${path.module}/${source.key}.txt"
        }
      }
    }
    ```
    

## 조건식

- 조건식은 3항 연산자 형태를 가짐
- ?를 기준으로 왼쪽은 조건, 오른쪽은 : 기호를 기준으로 왼쪽이 조건에 대해 true가 반환, 오른쪽이 false가 반환
- 조건식 형태와 예시
    
    ```hcl
    # <조건 정의> ? <옳은 경우> : <틀린 경우>
    var.a != "" ? var.a : "default-a"
    ```
    
- 조건식 형태 권장사항
    
    ```hcl
    var.example ? 12 : "hello" # 비권장
    var.example ? "12" : "hello" # 권장
    var.example ? tostring(12) : "hello" # 권장
    ```
    
- 조건식과 count로 리소스 생성 여부 결정 예시
    
    ```hcl
    variable "enable_file" {
      default = true
    }
    
    resource "local_file" "foo" {
      count = var.enable_file ? 1 : 0
      content = "foo!"
      filename = "${path.module}/foo.bar"
    }
    
    output "content" {
      value = enable_file ? local_file.foo[0].content: ""
    }
    ```

## 프로비저너

- 프로비저너는 프로바이더로 실행되지 않는 커맨드와 파일 복사 같은 역할을 수행
    - 클라우드에 리눅스 VM을 생성하는 것에 더해 특정 패키지를 설치해야 하거나 파일을 생성해야 하는 경우
- 프로비저너로 실행된 결과는 테라폼의 상태 파일과 동기화되지 않으므로 프로비저닝에 대한 결과가 항상 같다고 보장할 수 없음
    
    → 프로비저너 사용을 최소화하는 것이 좋음
    
- 프로비저너 종류
    - file
    - local-exec
    - remote-exec

### 프로비저너 사용 방법

- 리소스 프로비저닝 이후 동작하도록 구성할 수 있음
    - AWS의 EC2 인스턴스를 생성하고 난 후 CLI로 별도 작업을 수행하는 상황 가정
        
        ```hcl
        variable "sensitive_content" {
          default = "secret"
          sensitive = true
        }
        
        resource "local_file" "foo" {
          content = upper(var.sensitive_content)
          filename = "${path.module}/foo.bar"
        
          provisioner "local-exec" {
            command = "echo The content is ${self.content}"
          }
        
          provisioner "local-exec" {
            command = "abc"
            on_failure = continue
          }
        
          provisioner "local-exec" {
            when = destroy
            command = "echo The deleting filename is ${self.filename}"
          }
        }
        ```
        
- 프로비저너는 선언된 리소스 블록의 작업이 종료되고 나서 지정한 동작을 수행
- 다수의 프로비저너를 반복적으로 선언할 수 있으며 순서대로 처리
- 프로비저너에서는 self 값에 대한 참조 가능
    - 리소스 프로비저닝 작업 후 해당 속성 값들을 참조
- 프로비저너의 동작은 실행 계획만으로는 그 결과를 유추할 수 없음
    
    ```bash
    $ terraform apply
    ...
    local_file.foo: Creating...
    local_file.foo: Provisioning with 'local-exec'...
    local_file.foo (local-exec): (output suppressed due to sensitive value in config)
    local_file.foo (local-exec): (output suppressed due to sensitive value in config)
    local_file.foo: Provisioning with 'local-exec'...
    local_file.foo (local-exec): Executing: ["cmd" "/C" "abc"]
    local_file.foo (local-exec): 'abc' is not recognized as an internal or external command,
    local_file.foo (local-exec): operable program or batch file.
    local_file.foo: Creation complete after 0s [id=3c3b274d119ff5a5ec6c1e215c1cb794d9973ac1]
    
    Apply complete! Resources: 1 added, 0 changed, 0 destroyed.
    ```
    

### local-exec 프로비저너

- local-exec은 테라폼이 실행되는 환경에서 수행할 커맨드를 정의
    - 테라폼을 실행하는 환경에 맞게 설정 커맨드를 정의해야 함
- 사용하는 인수 값
    - command(필수)
        - 실행할 명령줄을 입력
        - << 연산자로 여러 줄의 커맨드 입력 가능
    - working_dir(선택)
        - command의 명령을 실행할 디렉터리를 지정해야 하고 상대/절대 경로로 설정
    - interpreter(선택)
        - 명령을 실행하는 데 필요한 인터프리터를 지정
        - 첫 번째 인수는 인터프리터 이름, 두 번째부터는 인터프리터 인수 값
    - environment(선택)
        - 실행 시 환경 변수는 실행 환경의 값을 상속
        - 추가 또는 재할당하려는 겨우 해당 인수에 key = value 형태로 설정

### 원격지 연결

- remote-exec와 file 프로비저너를 사용하기 위해서는 원격지에 연결할 SSH, WinRM 연결 정의가 필요
- connection 블록으로 원격지 연결 정의
    
    ```hcl
    resource "null_resource" "example1" {
      
      connection {
        type = "ssh"
        user = "root"
        password = var.root_password
        host = var.host
      }
    
      provisioner "file" {
        source = "conf/myapp.conf"
        destination = "/etc/myapp.conf"
      }
    
      provisioner "file" {
        source = "conf/myapp.conf"
        destination = "C:/App/myapp.conf"
    
        connection {
          type = "winrm"
          user = "Administrator"
          password = var.admin_password
          host = var.host
        }
      }
    }
    ```
    
    - connection 블록은 리소스에 선언되는 경우 해당 리소스 내에 구성된 프로비저너에 대해 공통으로 선언
    - 프로비저너 내에 선언되는 경우 해당 프로비저너에만 적용
- 원격 연결이 요구되는 프로비저너의 경우 스크립트 파일을 원격 시스템에 업로드해 해당 시스템의 기본 쉘에서 실행되도록 함
    
    → script_path의 경우 적절한 위치를 지정하도록 함
    
- 배스천 호스트를 통해 연결하는 경우 관련 인수를 지원
    - 보안을 위해 고안된 게이트웨이용 호스트, 외부 네트워크와 내부 네트워크 사이를 이어주는 역할

### file 프로비저너

- file 프로비저너는 테라폼을 실행하는 시스템에서 연결 대상으로 파일 또는 디렉터리를 복사하는 데 사용
- 사용되는 인수
    - source
        - 소스 파일 또는 디렉터리
        - 현재 작업 중인 디렉터리에 대한 상대 경로 또는 절대 경로로 지정할 수 있음
        - content와 함께 사용할 수 없음
    - content
        - 연결 대상에 복사할 내용을 정의하며 대상이 디렉터리인 경우 tf-file-content 파일이 생성되고 파일인 경우 해당 파일에 내용이 기록됨
        - source와 함께 사용할 수 없음
    - destination
        - 필수 항목으로 항상 절대 경로로 지정되어야 함
        - 파일 또는 디렉터리
- destination 지정 시 주의할 점은 ssh 연결의 경우 대상 디렉터리가 존재해야 함
- winrm 연결은 디렉터리가 없는 경우 자동으로 생성
- 디렉터리를 대상으로 하는 경우 source 경로 형태에 따라 동작에 차이가 생김
- file 프로비저너 구성 예
    
    ```hcl
    resource "null_resource" "" {
      
      # myapp.conf 파일이 /etc/myapp.conf로 업로드
      provisioner "file" {
        source = "conf/myapp.conf"
        destination = "/etc/myapp.conf"
      }
    
      # content의 내용이 /tmp/file.log 파일로 생성
      provisioner "file" {
        content = "ami used: ${self.ami}"
        destination = "/tmp/file.log"
      }
    
      # configs.d 디렉터리가 /etc/configs.d로 업로드
      provisioner "file" {
        source = "conf/configs.d"
        destination = "/etc"
      }
    
      # apps/app1 디렉터리 내의 파일들만 D:/IIS/webapp1 디렉터리 내에 업로드
      provisioner "file" {
        source = "apps/app1/"
        destination = "D:/IIS/webapp1"
      }
    }
    ```
    

### remote-exec 프로비저너

- remote-exec는 원격지 환경에서 실행할 커맨드와 스크립트를 정의
    - AWS의 EC2 인스턴스를 생성하고 해당 VM에서 명령을 실행하고 패키지를 설치하는 등의 동작을 의미
- 사용되는 인수
    - inline
        - 명령에 대한 목록으로 [] 블록 내에 “ ”로 묶인 다수의 명령을 ,로 구분해 구성
    - script
        - 로컬의 스크립트 경로를 넣고 원격에 복사해 실행
    - scripts
        - 로컬의 스크립트 경로의 목록으로 [] 블록 내에 “ ”로 묶인 다수의 스크립트 경로를 ,로 구분해 구성
- file 프로비저너 구성 예
    
    ```hcl
    resource "aws_instance" "web" {
      # ...
    
      connection {
        type = "ssh"
        user = "root"
        password = var.root_password
        host = self.public_ip
      }
    
      provisioner "file" {
        source = "script.sh"
        destination = "/tmp/script.sh"
      }
    
      provisioner "remote-exec" {
        inline = [
          "chmod +x /tmp/script.sh"
          "/tmp/script.sh args"
        ]
      }
    }
    ```
    

## null_resource와 terraform_data

- null_resource를 대체하는 terraform_data 리소스가 추가

### null_resource

- 아무 작업도 수행하지 않는 리소스를 구현
- 테라폼 프로비저닝 동작을 설계하면서 사용자가 의도적으로 프로비저닝하는 동작을 조율해야 하는 상황이 발생, 프로바이더가 제공하는 리소스 수명주기 관리만으로는 이를 해결하기 어려움
- 주로 사용되는 시나리오
    - 프로비저닝 수행 과정에서 명령어 실행
    - 프로비저너와 함께 사용
    - 모듈, 반복문, 데이터 소스, 로컬 변수와 함께 사용
    - 출력을 위한 데이터 가공
- 예시
    - AWS EC2 인스턴스를 프로비저닝하면서 웹서비스를 실행시키고 싶음
    - 웹서비스 설정에는 노출되어야 하는 고정된 외부 IP가 포함된 구성이 필요함
        
        → aws_eip 리소스를 생성해야 함
        
    - aws_instance에서 aws_eip의 public ip를 사용하려는 예
        
        ```hcl
        # ...
        resource "aws_instance" "foo" {
          ami = "ami-5189a661"
          instance_type = "t2.micro"
        
          private_ip = "10.0.0.12"
          subnet_id = aws_subnet.tf_test_subnet_id
        
          provisioner "remote-exec" {
            inline = [
              "echo ${aws_eip.bar.public_ip}"
            ]
          }
        }
        
        resource "aws_eip" "bar" {
          vpc = true
        
          instance = aws_instance.foo.id
          associate_with_private_ip = "10.0.0.12"
          depeneds_on = [aws_internet_gateway.gw]
        }
        ```
        
        - aws_eip가 생성하는 고정된 IP를 할당하기 위해서는 대상인 aws_instance의 id 값이 필요함
        - aws_instance의 프로비저너 동작에서는 aws_eip가 생성하는 속성 값인 public_ip가 필요함
    - 이 경우 상호 참조가 발생
        
        → 둘 중 하나의 실행 시점을 한 단계 뒤로 미뤄야 함
        
        → 실행에 간격을 추가해 실제 리소스와는 무관한 동작을 수행하기 위해 null_resource를 활용
        
    - 아래와 같이 수정
        
        ```hcl
        resource "aws_instance" "foo" {
          ami = "ami-5189a661"
          instance_type = "t2.micro"
        
          private_ip = "10.0.0.12"
          subnet_id = aws_subnet.tf_test_subnet_id
        
          provisioner "remote-exec" {
            inline = [
              "echo ${aws_eip.bar.public_ip}"
            ]
          }
        }
        
        resource "aws_eip" "bar" {
          vpc = true
        
          instance = aws_instance.foo.id
          associate_with_private_ip = "10.0.0.12"
          depeneds_on = [aws_internet_gateway.gw]
        }
        
        resource "null_resource" "barz" {
          provisioner "remote-exec" {
            connection {
              host = aws_eip.bar.public_ip
            }
            inline = [
              "echo ${aws_eip.bar.public_ip}"
            ]
          }
        }
        ```
        
        - null_resource는 정의된 속성이 id가 전부이므로 선언된 내부의 구성이 변경되더라도 새로운 plan 과정에서 실행 계획에 포함되지 못함
        
        → 따라서 사용자가 null_resource에 정의된 내용을 강제로 다시 실행하기 위한 인수로 trigger가 제공
        
        - trigger는 임의의 string 형태의 map 데이터를 정의하는데 정의된 값이 변경되면 null_resource 내부에 정의된 행위를 다시 실행
        - trigger 정의와 동작 예시
            
            ```hcl
            resource "null_resource" "foo" {
              trigger = {
                ec2_id = aws_instance.bar.id # instance의 id가 변경되는 경우 재실행
              }
              # ...
            }
            
            resource "null_resource" "barz" {
              trigger = {
                ec2_id = time() # 테라폼으로 실행 계획을 생성할 때마다 재실행
              }
              # ...
            }
            ```
            

### terraform_data

- terraform_data 리소스 또한 자체적으로 아무것도 수행하지 않음
- 추가 프로바이더 없이 테라폼 자체에 포함된 기본 수명주기 관리자가 제공되는 것이 장점
- 사용 시나리오는 null_resource와 동일
    - 강제 재실행을 위한 triggers_replace
        - 정의되는 값이 map에서 tuple로 변경
    - 상태 저장을 위한 input 인수
    - input에 저장된 값을 출력하는 output 속성이 제공
- trigger_replace 정의와 동작 예제
    
    ```hcl
    resource "terraform_data" "foo" {
      triggers_replace = [
        aws_instance.bar.id,
        aws_isntance.barz.id
      ]
    
      input = "world"
    }
    
    output "terraform_data_output" {
      value = terraform_data.foo.output # 출력 결과는 "world"
    }
    ```
    

## moved 블록

- 테라폼 리소스를 선언하다 보면 이름을 변경해야 하는 상황이 발생하기도 함
    - 리소스 이름을 변경
    - count로 처리하던 반복문을 for_each로 변경
    - 리소스가 모듈로 이동하여 참조되는 주소가 변경
- 리소스의 이름은 변경되지만 이미 프로비저닝된 환경을 그대로 유지하고자 하는 경우 moved 사용 가능
- 테라폼 State에서 옮겨진 대상의 이전 주소와 새 주소를 알리는 역할 수행
- moved 블록은 State에 접근 권한이 없는 사용자라도 변경되는 주소를 리소스 영향 없이 반영할 수 있음
- moved 블록 예시
    
    ```hcl
    resource "local_file" "a" {
      content = "foo!"
      filename = "${path.module}/foo.bar"
    }
    
    output "file_content" {
      value = local_file.a.content
    }
    ```
    
    - local_file의 이름은 a를 b로 변경해야 한다고 가정
    
    ```hcl
    resource "local_file" "b" {
      content = "foo!"
      filename = "${path.module}/foo.bar"
    }
    
    moved {
      from = local_file.a
      to = local_file.b
    }
    
    output "file_content" {
      value = local_file.b.content
    }
    ```
    
    - moved 블록으로 변경되는 주소를 명시
    
    ```bash
    $ terraform plan
    Acquiring state lock. This may take a few moments...
    local_file.b: Refreshing state... [id=4bf3e335199107182c6f7638efaad377acc7f452]
    
    Terraform will perform the following actions:
    
      # local_file.a has moved to local_file.b
        resource "local_file" "b" {
            id                   = "4bf3e335199107182c6f7638efaad377acc7f452"
            # (10 unchanged attributes hidden)
        }
    
    Plan: 0 to add, 0 to change, 0 to destroy.
    ```
    
    - 제거되거나 생성되는 리소스는 없고 출력 결과에 local_file.a 주소가 local_file.b로 변경되었다는 메시지가 추가로 출력

## CLI를 위한 시스템 환경 변수

- 환경 변수를 통해 실행 방식과 출력 내용에 대한 옵션을 조절할 수 있음
- 시스템 환경 변수를 설정하면 영구적으로 로컬 환경에 적용되는 옵션이나 별도 서버 환경에서 실행하기 위한 옵션을 부여할 수 있음
- 로컬 작업 환경과 다른 환경 구성에서만 사용될 특정 옵션을 적용
    - MAC/Linux/Unix
        - export <환경 변수 이름>=<값>
    - Windows CMD
        - set <환경 변수 이름>=<값>
    - Windows PowerShell
        - $Env:<환경 변수 이름>=<값>

### TF_LOG

- 테라폼의 stderr 로그에 대한 레벨을 정의
- trace, debug, info, warn, error, off를 설정할 수 있고 관련 환경 변수가 없는 경우 off와 동일
- 디버깅을 위한 로그 관련 환경 변수
    - TF_LOG
        - 로깅 레벨 지정 또는 해제
    - TF_LOG_PATH
        - 로그 출력 파일 위치 지정
    - TF_LOG_CORE
        - TF_LOG와 별도로 테라폼 자체 코어에 대한 로깅 레벨 지정 또는 해제
    - TF_LOG_PROVIDER
        - TF_LOG와 별도로 테라폼에서 사용하는 프로바이더에 대한 로깅 레벨 지정 또는 해제

### TF_DATA_DIR

- 작업 디렉터리별 데이터를 보관하는 위치를 지정
- 이 데이터는 .terraform 디렉터리 위치에 기록되지만 TF_DATA_DIR에 경로가 정의되면 기본 경로를 대체하여 사용
- 일관된 테라폼 사용을 위해서 해당 변수는 실행 시마다 일관되게 적용되도록 설정하는 것이 중요함
- 설정 값이 이전 실행 시에만 적용되는 경우 init 명령으로 수행된 모듈, 아티팩트 등의 파일을 찾지 못함
- terraform init이 수행된 상태에서 TF_DATA_DIR로 경로를 재지정하고 실행하는 경우 플러그인 설치가 필요하다는 메시지를 출력
